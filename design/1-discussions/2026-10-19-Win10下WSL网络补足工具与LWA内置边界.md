# Win10 下 WSL 网络补足工具与 LWA 内置边界

日期：2026-10-19。状态：调研讨论已按用户意见收紧边界；不将第三方网络工具或自有 Windows 规则维护组件纳入当前内置范围。未安装工具、未改机器配置。
关联：BUG-923、PLN-054。本文只含通用规则和公开项目资料，不包含真实 SSH、主机地址或账号。

## 1. 要解决的用户问题

用户希望探讨：Win10 没有原生 mirrored 时，是否可通过安装工具获得类似体验，LWA 是否应内置这种补足能力。

这里区分两个目标：

1. **网页访问体验**：其他局域网设备使用浏览器即可访问 WSL 中的 LWA 应用；入口受用户已有网络配置和策略约束。LWA 应正确发现、解释、验证现有入口，缺少转发时提供透明说明，由用户决定是否修改系统配置。
2. **完整网络语义**：mirrored 涉及接口、Windows/guest 互通、IPv6/多播等能力。一个 TCP 转发工具不等于把 Win10 改造成原生 mirrored 环境；目前查到的资料不能支持“安装某工具即可完整替代”的承诺。[微软网络说明](https://learn.microsoft.com/en-us/windows/wsl/networking)

LWA 的首要需求是应用网页入口。用户进一步明确不应为此改变既有网络结构或接管网络设施；撤回此前向“内置可选 Windows 网络辅助/自动规则维护”推进的建议。下文保留工具原理供理解边界，不构成引入计划。

## 2. 路线与候选

以下能力来自当前官方文档或项目 README；对本项目环境的适用性仍待实测，评价为本项目的选型判断。

| 路线 | 能力与边界 | 对 LWA 的建议 |
| --- | --- | --- |
| Windows 自带 portproxy + 定向防火墙规则 | 系统提供 TCP 代理，微软给出 NAT 下转发到 guest IP 的示例；新增规则同样改变服务暴露范围。[WSL 官方说明](https://learn.microsoft.com/en-us/windows/wsl/networking)、[netsh 命令](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-interface) | 属用户维护的系统配置；LWA 当前只读诊断与提供可审阅说明，不创建或自动维护规则 |
| wsl2-auto-portproxy / wslpp | 当前 README 描述了 IP/端口扫描、代理、预定义端口、指定发行版、客户端 allowlist 和 Windows 后台任务等功能；新增代理监听不必然改动路由拓扑，但会改变服务暴露与运行依赖。[项目](https://github.com/HobaiRiku/wsl2-auto-portproxy) | 保留为外部工具资料，不纳入当前内置、安装或托管范围 |
| frp | 支持 TCP/UDP/HTTP(S) 等代理，通过客户端与服务端组织连接；需要维护额外进程和配置。[项目](https://github.com/fatedier/frp) | 不为当前 WSL 适配引入；用户已有入口可作为显式配置的候选，仍需验证 |
| Tailscale Serve | 为 tailnet 内设备提供本地服务访问，并有自身身份、证书和访问控制体系。[官方说明](https://tailscale.com/docs/features/tailscale-serve) | 不替用户引入组网体系；用户已有私网入口可显式配置，但不据此声称普通 LAN 设备均可达 |
| wsl-vpnkit | 主要解决 Windows VPN 阻断 WSL 网络连通的场景。[项目](https://github.com/sakai135/wsl-vpnkit) | 不在本次适配中安装或管理；VPN 环境作为用户现有条件进行诊断 |
| WSLHostPatcher | README 明确通过注入 wslhost.exe、hook bind 来改变接口监听，重启后需重新应用。[项目](https://github.com/CzBiX/WSLHostPatcher) | 不集成；不修改用户 WSL 系统进程的监听行为 |

wslpp 的 README 正在演进：当前文档已有显式 distro、可选 UDP 与后台任务等说明，不能根据旧搜索摘要认定它始终只支持默认发行版或只支持 TCP。最终评价需冻结提交/发行版并核对实现，不能只凭 README 功能列表宣布通过。

## 3. 按用户意见确定的当前边界

**LWA 适配用户已有网络：只读识别、正确展示、分层诊断与配置说明。当前不内置网络改造或第三方工具托管。**

- LWA 主程序继续运行在 Linux/WSL 中；不新增 Windows 常驻代理、任务计划、服务、网卡或组网客户端。
- 只读获取模式、入口、已有映射、监听、权限和证据；不改网卡、路由、DNS、VPN、网络模式、防火墙或 portproxy，也不提权尝试绕过读取限制。
- 在用户已有转发或 mirrored 环境中正确推导入口；用户也可显式提供外部入口信息，但在缺少外部证据时标作候选。
- 未建立 LAN 暴露路径时，明确显示本地仍可用及 LAN 不可用/未知的原因，提供可审阅的系统配置说明，由用户或管理员选择是否执行。可选系统命令也不能伪装成“零侵入”自动执行。
- 地址或规则变化后重新诊断并指出漂移，不自动修复或覆盖用户配置；冲突显示出来，不抢占端口。
- 读取被拒时保留 unknown；不要将无权限解释成无规则，也不建议用户关闭安全设施来让诊断通过。
- 正确兼容现有 HTTP/HTTPS、来源身份与鉴权边界；这些是 LWA 自身应修复的契约，不依赖额外安装网络工具。

## 4. 下一步验证范围

| 场景 | 需要回答的问题 |
| --- | --- |
| 用户已有 NAT/系统转发 | 能否只读识别监听、目标、端口转换及漂移？无转发、转发冲突、无权限时是否明确说明而不假绿？ |
| 用户已有 mirrored/其他入口 | 能否区分运行模式和入口范围？正确处理 Windows/WSL 版本、网卡及现有防火墙带来的差异？ |
| 用户未配置外部入口 | 本地功能是否继续可用？LAN 不可达的原因、候选地址和用户可审阅的处置步骤是否清楚？ |

验证仍覆盖外部浏览器访问 HTML/CSS/JS、WebSocket、HTTPS/鉴权、休眠恢复、WSL IP 变化、多发行版、多工作区、Win10/11 与包版本组合及非管理员诊断。测试环境的配置变更由用户/管理员明确控制，不由 LWA 隐式执行。

本轮不再安排“安装网络工具或常驻规则维护”作为该适配计划的实施原型。将来若出现独立的明确需求，需重新讨论产品范围，不能沿用本次调研推定已有安装授权。

## 5. 修订结论

- 工具对环境的影响不同：端口代理、私网组网、系统进程注入不能统称同一种网络拓扑修改；但均不属于 LWA 当前默认安装或托管范围。
- 撤回此前将系统自动规则维护与 wslpp 列为内置辅助原型的建议；当前以本修订后的边界为准。
- 跨版本适应性落实为尊重现有网络、准确识别、诚实展示可达范围、分层验证和清楚解释缺失条件。
- 没有可用 LAN 入站路径时，诊断本身不能创造外部连通性；LWA 应把限制说明白，网络配置决策归用户。
- BUG-923 的地址语义、诊断与 HTTPS/鉴权契约仍需修复；PLN-054 保留跨版本验收，不引入上述网络改造依赖。

## 1. 文档目的

2608 §12 适合保存 IMP-055 的职责边界、决策和 WBS，但没有完整保存后续多轮代码复核与实机验证过程。本复盘补齐以下信息：

1. 为什么 `/<alias>/` 能返回 200，页面仍会白屏或 API 失效。
2. 为什么最初的网关 `/assets` 回退只能救急，不能作为通用方案。
3. 为什么项目侧必须采用显式 base path，而不是只把少数资源改成相对路径。
4. LWA 如何从“允许设置别名”演进为“设置前门禁 + 运行后复核 + 可解释报告”。
5. 为什么第一轮 BUG-467～469 修复在单测全绿后仍被真实 home-bookshelf 推翻。
6. 最终如何用别名感知 URL 解析、MIME 校验和证据分级完成负向识别闭环。
7. prd-review 与 home-bookshelf 最新版的真实正向 E2E 覆盖了什么、没有覆盖什么。

## 2. 系统模型：浏览器、Caddy 与应用各看到什么

LWA 的路径别名由 Caddy `handle_path` 实现：

```caddyfile
handle_path /home-bookshelf/* {
    reverse_proxy 127.0.0.1:18009
}
```

请求在三层中的路径如下：

```text
浏览器请求 /home-bookshelf/api/v1/members
        ↓
Caddy 匹配 /home-bookshelf/*，去掉别名前缀
        ↓
后端收到 /api/v1/members
```

这意味着后端通常不需要把自身路由改成 `/home-bookshelf/api/...`；真正需要感知别名的是浏览器侧生成的 URL。

### 2.1 三类浏览器地址

| HTML / JS 写法 | 浏览器在 `/<alias>/` 页面中的请求 | 结果 |
| --- | --- | --- |
| `./assets/app.js` | `/<alias>/assets/app.js` | 通常正确 |
| `/<alias>/assets/app.js` | `/<alias>/assets/app.js` | 正确，适合固定别名部署 |
| `/assets/app.js` | `/assets/app.js` | 绕过别名，落到入口根，错误 |

API 与 Router 完全遵循同一规则：绝对 `/api/v1` 和根历史路由 `/books/1` 都会丢失别名前缀。

## 3. 问题发现：入口 200 不等于应用可用

### 3.1 初始症状

访问：

```text
http://10.180.106.12:8080/home-bookshelf/
```

最初观察到：

- 容器正常运行，`18009` 可达。
- Caddy 别名入口返回 200。
- 页面仍白屏或业务数据无法加载。
- `lwa access review` 一度返回 `overall=ok`。

### 3.2 逐层取证

CHK-180 对运行日志、Caddy 路由和 HTTP 响应进行对照后确认：

- HTML 由 `/<alias>/` 正常返回。
- HTML 内仍引用 `/assets/...`、`/favicon.svg` 等根绝对资源。
- 浏览器因此请求统一入口根 `/assets/...`，没有进入 home-bookshelf 的别名 handler。
- 入口根可能返回空 200、404，或者被另一个 SPA fallback 吃成 `200 + text/html`。
- 前端 API 客户端仍使用绝对 `/api/v1`；根 `/api/v1/...` 与 `/<alias>/api/v1/...` 的响应不一致。
- Vue Router 使用无 base 的 history，深层导航也会丢失别名前缀。

问题因此不是单一的“静态文件 404”，而是三个浏览器侧基址同时错误：

1. 构建产物资源 base；
2. Router history base；
3. API client base。

## 4. 项目源码分析与最终应用侧方案

CHK-181 确认 home-bookshelf 拥有完整源码：

```text
home-bookshelf-management-v1/
├── frontend/
└── backend/
    └── static/       # LWA 容器实际服务的生产前端
```

最初源码状态为：

| 触点 | 原状态 | 别名下后果 |
| --- | --- | --- |
| Vite | 默认 `base: '/'` | 生成 `/assets/...` |
| Vue Router | `createWebHistory()` | 深层路由跳到域名根 |
| API store | `BASE='/api/v1'` | 请求统一入口根 API |

最终应用侧采用显式 base path：

```text
vite build --base=/home-bookshelf/
createWebHistory(import.meta.env.BASE_URL)
API base 从 import.meta.env.BASE_URL 派生
```

构建完成后必须把 `frontend/dist/` 同步到 `backend/static/`，再由 LWA “从源更新”并重建容器。

`base: './'` 只能部分修复入口页资源引用；在 history 深层路由和相对 API fetch 场景下仍可能解析到错误目录，因此不是最终推荐方案。

## 5. 方案演进：哪些尝试有效，哪些被否决

### 5.1 BUG-465：网关 `/assets` 回退

第一轮救急方案是在 docker-compose 别名片段中增加 `/assets/*`、`/favicon.*` 到同一后端的回退。

它能让单个 home-bookshelf 的静态资源暂时恢复，但存在结构性问题：

- 多个实例都声明 `/assets` 时无法确定归属。
- 无法修复绝对 `/api`。
- 无法修复 Router history。
- 会把“入口能打开”误当成“项目已兼容子路径”。

IMP-055 最终把该能力降级为 `spa_fallback=True` 显式逃生舱，默认 `False`；新生成别名配置不再自动添加全局回退。

### 5.2 BUG-466：设置别名前硬拦截

LWA 增加 `reject_alias_if_absolute_spa_assets`：如果能取得入口 HTML 并发现根绝对 `src`/`href`，`lwa alias set` 与管理页设置别名直接抛出 `RecognitionError`。

失败文案明确给出：

- Vite `--base=/<alias>/`；
- Router 使用 `BASE_URL`；
- API 从 `BASE_URL` 派生；
- 同步构建产物；
- 无源码时继续使用 hostPort。

IMP-055 撤销了 docker-compose 因 BUG-465 回退而获得的守卫豁免，shared-static 与 docker-compose 使用同一门禁。

当入口 HTML 取不到时，LWA 不做无证据硬拦截，而通过 `PathAliasResult.html_verified=false` 告知调用方“别名已设置，但入口 HTML 未验证”。

### 5.3 方案 B：应用显式 base path

最终职责划分为：

| 责任方 | 责任 |
| --- | --- |
| 应用项目 | 正确生成静态资源、Router 与 API URL |
| LWA | 提供 `handle_path` 路由、设置前门禁、运行后复核和清晰诊断 |
| LWA 不负责 | 自动重写第三方 bundle、猜测并修改业务路由、用全局 `/assets` 冒充兼容 |

## 6. IMP-055 第一轮平台实现

### 6.1 文档与 Skill 口径

`docs/known-limitations.md`、`docs/faq.md`、`lwa-import-zip` 和 `lwa-build-frontend-static` 统一为“显式、可配置 base path”，并把应用分为：

- A：已兼容子路径，可直接使用别名；
- B：有源码，改造 base 后可使用；
- C：无源码或无法重建，路径别名模型无解，使用 hostPort。

### 6.2 网关与设置门禁

- `static_gateway.generate_alias_config(..., spa_fallback=False)` 默认关闭 BUG-465 回退。
- `path_alias.py` 对所有 runtime 执行入口 HTML 守卫。
- CLI 仅在 `html_verified=false` 时提示残余风险。
- 管理页复用同一 `RecognitionError`，不再出现“保存成功但页面不可用”。

### 6.3 `access review` API 对照

新增 `ApiPathFinding`，对照：

```text
/api/...                  # 入口根绝对路径
/<alias>/api/...          # 带别名前缀路径
```

根路径空 200/失败、而前缀路径有实体时，实例降为 warn，并在 JSON 与人类报告中输出 API 路径错位。

## 7. 第一轮“已完成”复核为何被推翻

初次实现全量测试为 1731 passed、4 skipped，但 CHK-182 代码复核发现三项未闭环问题。

### 7.1 BUG-467：真实 API 仍漏报

第一版只从入口 HTML 抽取 `/api/...`，而 home-bookshelf 的 API 常量在外链 JS bundle 内。默认只探测 `/api/`、`/api/v1/`，前缀根路径又返回 JSON 404，因此 `mismatch=false`，已知坏实例仍为 `overall=ok`。

### 7.2 BUG-468：聚合和建议输出错误

- `has_api_mismatch` 曾使用 `bool(api_findings)`，只要探测过就可能误报。
- `format_rebuild_advice` 在没有静态 rebuild 候选时提前返回，API-only mismatch 没有建议段。

修复后改为 `any(f.mismatch for f in api_findings)`，且 API-only mismatch 能独立输出方案 B 指引。

### 7.3 BUG-469：导入阶段绕过硬守卫

`set_instance_path_alias` 会执行守卫，但 `import --path-alias` 原本只校验格式、唯一性和网关类型，随后直接把 `routeMode=name/routeHost` 写入 manifest。

修复后 Importer 在 manifest 落盘前读取解压目录入口 HTML，并复用同一个 `reject_alias_if_absolute_spa_assets`；失败时清理半成品，`RecognitionError` 原样透出。

## 8. 第二轮假绿：模拟 bundle 与真实 bundle 不一致

第一轮 BUG-467 修复增加了 JS bundle 抽取，并用以下模拟形式验证：

```js
const endpoint = "/api/v1/members"
```

真实 home-bookshelf bundle 却是：

```js
const BASE = "/api/v1"
fetch(`${BASE}${endpoint}`)
get("/members")
```

探测只能获得 `/api/v1`，而 `/<alias>/api/v1` 本身是合法后端返回的 JSON 404，不是 2xx，第一版规则仍判 `mismatch=false`。这说明“测试像项目”不等于“测试就是项目”，必须保留真实构建产物形态的负向样本。

## 9. 真实正向 E2E 与重复别名前缀问题

2026-08-10，使用当前未提交 LWA 代码升级 prd-review 和 home-bookshelf 最新版本后，运行日志显示：

- 两个镜像构建成功；
- 容器完成重建并持续 Up；
- Uvicorn application startup complete；
- Caddy 别名片段均使用 `handle_path`；
- home-bookshelf 数据库迁移正常。

Playwright 正向验证：

| 项目 | 验证结果 |
| --- | --- |
| home-bookshelf 首页 | 页面渲染、成员/图书/统计/封面 API 全部成功 |
| home-bookshelf 深层路由 | `/home-bookshelf/books/1` 直接刷新成功，详情 API 200 |
| prd-review 首页 | CSS、JS、vendor、branding API 全部成功 |
| 浏览器请求 | 所有请求均保留各自别名前缀 |
| 控制台/网络 | 无 console error、requestfailed 或 HTTP 错误 |
| LAN | `10.180.106.12:8080` 的入口、API、深层路由均为 200 |

正向部署链路因此通过。但 `static-access.log` 同时暴露了新的复核器问题：兼容版 HTML 已写：

```html
<script src="/home-bookshelf/assets/index.js">
```

旧 `_collect_api_paths` 生成：

```text
hostPort: /home-bookshelf/assets/index.js       # 后端真实路径应为 /assets/index.js
gateway:  /home-bookshelf/home-bookshelf/assets/index.js
```

错误路径又被 SPA fallback 返回成 HTML 200，使 bundle 抽取继续假绿。

## 10. BUG-467 最终修复

### 10.1 别名感知 script URL 解析

新增 `_resolve_alias_aware_script_urls`，统一三种 HTML 写法：

| `script src` | 后端直连路径 | 网关路径 |
| --- | --- | --- |
| `/assets/app.js` | `/assets/app.js` | `/<alias>/assets/app.js` |
| `./assets/app.js` | `/assets/app.js` | `/<alias>/assets/app.js` |
| `/<alias>/assets/app.js` | `/assets/app.js` | `/<alias>/assets/app.js` |

已带前缀时先剥离一次，再为网关添加一次，从结构上禁止 `/<alias>/<alias>/...`。

### 10.2 MIME 校验

新增 `_fetch_javascript`：只有响应 `Content-Type` 明确为 JavaScript 才解析正文。`200 + text/html` 的 SPA fallback 不再被当作 bundle。

### 10.3 “已发现路径”与“默认兜底”分流

API 路径分为：

- `discovered`：确实从 HTML/JS bundle 发现；
- `default`：没有发现时才尝试的 `/api/`、`/api/v1/`。

经典 mismatch 仍要求根空/失败且前缀 2xx 有实体。

对于明确发现的绝对 API 基址，增加高置信疑似判定：

```text
根 /api/v1                 -> 空 200 或失败
前缀 /<alias>/api/v1      -> 非空 application/json 404
```

这证明根绝对请求落入错误入口，而带前缀请求已经到达应用 API router。无需尝试对压缩 JavaScript 做完整数据流分析，也能覆盖 `BASE + endpoint` 拼接形态。

默认兜底路径不得使用该 JSON 404 规则，否则无 API 项目会被误报。

## 12. 当前能力边界

1. `access review` 是有界抽样，不是通用 JavaScript 数据流分析器。
2. JSON 404 规则只用于 bundle 明确发现的绝对 API 基址，并以 warn 表达高置信风险。
3. 深层路由无法穷举；目前以真实 `/books/1` 和项目自有测试抽样。
4. 固定 `/<alias>/` base 后，别名 URL 是正式入口；hostPort 根路径前端可能不再完整。
5. LWA 不自动修改第三方源码或构建产物。
6. 无源码/无法重建项目仍应使用 hostPort；主机名别名可作为未来独立功能。
7. 正向 E2E 未覆盖 prd-review 登录后的全部写操作，也未覆盖 home-bookshelf 所有业务变更；本轮验证目标是子路径部署链路。

## 14. 关键经验

1. **入口 200 不是可用性证明**：必须继续验证资源、API、Router 与 MIME。
2. **网关回退不是应用兼容性**：它可能遮住错误，并在多实例中产生路由归属冲突。
3. **正向与负向样本必须同时存在**：新版项目证明能用，旧版 fixture 证明平台能识别不能用。
4. **模拟测试必须保持真实构建形态**：完整 `/api/v1/members` 字面量不能代表 `BASE + endpoint`。
5. **证据要分级**：默认猜测不能触发强告警；从真实 bundle 发现的路径可以使用更强判定。
6. **项目侧与平台侧职责要分开**：应用负责生成正确 URL，LWA 负责路由、门禁、诊断与解释。

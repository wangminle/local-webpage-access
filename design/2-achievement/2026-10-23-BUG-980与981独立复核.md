## 审查发现

### BUG-982 / P2：启动前全量诊断可能耗尽管理服务启动预算

位置：`src/local_webpage_access/manager_api.py:441`。

新增 `_compute_loopback_identity_trusted` 同步调用完整 WSL 网络采集。该函数在 `create_app` 中执行，`run_manager` 等它返回后才创建 uvicorn 并开始监听。完整采集串行执行版本、模式、网卡、路由、portproxy、监听、防火墙等查询，各条命令可等待 5 秒；`start_manager` 的健康等待预算只有 15 秒。

受控探针让 `wslinfo` 立即返回 NAT，仅让三个与信任判定无关的 Windows 诊断各耗尽 5 秒，真实判定函数耗时 15.079 秒、执行 10 条命令，已经超出父进程等待预算。慢互操作下，即使 NAT 模式早已明确，也可能尚未监听就被父进程判启动失败并终止。现有新增测试直接替换采集函数，未覆盖此时序。

建议：使用有总预算的轻量模式判定，或先保持回环不可信后异步完成必要探测；不能在尚未取得证据时先启用免 token。增加慢查询下管理服务仍能及时启动的回归。该结果是受控函数时序复现，未在真实 Windows 上制造故障，也未实跑父进程杀服务。

### BUG-983 / P2：Agent M1 的本机身份判定未接入新信任状态

位置：`src/local_webpage_access/agent/auth.py:82`。

`authenticate_local_owner` 仍单独使用 peer 回环和回环 Host 判断本机，未消费 `app.state.loopback_identity_trusted`。使用已实测的 Windows 回环转发请求形态，在 ASGI 测试中设置该标记为 False、peer 为回环、Host 伪造为回环：同一请求在 manager 中被判为非本机，但 Agent 携带有效管理 token 时，`/api/agent/v1/capabilities` 和 `/instances` 均返回 200，主体为 `local_owner`。

这违反 M1 仅本机、远程主体留待 M2 的边界。无 token 或无效 token 仍返回 401；**不是无 token 鉴权绕过，也未证明获得超出有效管理 token 的既有权限**。不能据此宣称原 P1 漏洞仍然存在。

建议：Agent 使用一致的可信本机判定；同时验证 WSL 下真实本机 CLI/MCP 的接入或明确替代通道，避免仅通过全面拒绝而静默破坏既定 M1 能力。该复现没有重新建立真实 Windows 转发。

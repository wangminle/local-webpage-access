# LWA tests 与 gate.sh 机制经验总结

日期：2026-10-17。面向项目维护者及复用这套机制的开发者。

## 结论与证据口径

LWA 的测试提速效果明显。按 task-list.md 的 DEV-166 历史记录，全量 pytest 从约 493 秒降到消除真实等待后的串行 258 秒，再降到适度并行下的约 107 秒。对应减少约 78.3% 的等待时间，速度约为原来的 4.61 倍。

可复用的经验包括：先定位真实耗时来源，隔离测试不需要的等待与外部副作用；再按共享资源安排并行；将真实重型验证单独启用；通过统一入口、失败汇总和证据记录保持质量标准可见。

这里的“成功”指反馈效率、可重复性、环境隔离和失败暴露能力的改善。目前门禁仍会报告真实失败，不能据此宣称所有产品缺陷已经清零。

## 一、tests 的组织方式

当前顶层主要有三类内容：

| 位置 | 用途 | 对反馈效率的贡献 |
| --- | --- | --- |
| `tests/scripts/` | pytest 自动化用例、共享夹具和辅助模块 | 将日常回归集中到可筛选、可并行的测试集合 |
| `tests/fixtures/` | 小型样例项目，以源码字典按需生成 zip | 样例可审查、可复现，避免靠手工维护二进制包 |
| `tests/evals/` | 真实应用部署评测的本地源码 | 保留真实应用证据，同时避免 pytest 收集上游测试与 conftest |
| `tests/gate.sh` | 本地与 CI 的统一门禁入口 | 减少漏跑步骤和命令口径差异 |

本次文件盘点有 151 个 `test_*.py` 文件；其中 33 个文件名以 test_bug、test_issue 或 test_chk 开头，便于追踪历史问题。当前 `pytest --collect-only -q` 按文件统计共收集 3850 项；这只是当前收集快照，不冒充上一轮执行数量。

测试分层在逻辑上组织，物理上多数文件集中在 scripts/：

- 纯逻辑与本地数据测试：配置、模型、路径、扫描、SQLite registry、文件打包等。
- 模块集成测试：importer、hosting、lifecycle、daemon、manager API、更新与迁移等流程，外部进程和探针按用例目的替换。
- 外部工具语义测试：例如真实执行 `caddy adapt`，检查生成配置的解析结果。
- 显式启用的真实 Docker 测试：镜像构建、容器运行、非 root 写库、真实操作终态等。
- 独立真实应用 Eval：验证复杂上游工程、双机环境、业务操作和升级数据保留。

这套分层允许日常门禁快速覆盖大部分确定性行为，同时保留更高成本的现实验证。默认门禁通过不能代替 Docker 或完整业务验收。

## 二、统一 gate 的工程价值

当前 gate 顺序运行：Ruff → pytest → 工作区 diff-check → 暂存区 diff-check。

`run_step` 用条件分支记录每一步结果与耗时。即使某一步失败，后面的步骤仍会继续，最后统一打印 PASS/FAIL；任何一步失败都会让脚本退出 1。这使一次运行能提供完整诊断，而不会因为前面出错就丢掉后续检查结果。

本会话上一轮就是实际例子：pytest 失败后，两个 diff-check 仍执行，最终清楚显示只有 pytest 未通过。失败没有被其他成功步骤覆盖。

其他实用细节：

- 自动定位仓库根目录，降低从不同目录启动造成的差异。
- 优先选择可运行且满足 Python 版本要求的项目解释器，再尝试 uv、系统解释器；支持显式解释器路径覆盖。
- 用同一解释器的 `python -m ruff` 与 `python -m pytest`，减少全局工具和项目环境混用。
- pytest 固定 `LC_ALL=C LANG=C`，减少本地化差异。
- 显式固定 Ruff 规则范围为 E4/E7/E9/F；工具升级不会无声扩大默认规则口径。这不等于已经启用了全部风格规则或格式化检查。
- 透传 pytest 参数，支持按模块、关键词、单个用例定位问题。
- xdist 缺失时回退串行，额外依赖缺失不会让测试全部无法运行。

参数透传有明确边界：带 `-k` 或指定文件运行，只证明被选择的子集通过。完整提交门禁仍应运行不带筛选条件的命令。

## 三、等待优化：保留行为，减少真实耗时

DEV-166 排查到多处测试进入了生产等待：更新后探测真实服务、容器存活探针轮询、迁移后拉起真实 daemon，以及访问复核的 7.5 秒防抖。部分用例会等待完整的 30 秒窗口，且可能接触宿主机服务或留下进程。

当前做法根据测试目的区分：

1. **测试上层流程时，提供确定性的下层结果。** `test_updater.py` 的默认夹具将 `_service_ready` 设为已就绪；专门测试等待行为的用例自行覆盖。迁移测试替换真实 start_daemon 等外部副作用。
2. **测试等待算法时，模拟时钟。** 就绪与超时测试同时替换 `monotonic` 和 `sleep`，让 sleep 推进虚拟时间，断言第三次才就绪、超时后未就绪列表与等待时间。
3. **测试防抖策略时，记录等待序列。** 用例验证首查成功零等待、失败后成功时的重试次数、全部失败时的 `[0.5, 1.0, 2.0, 4.0]` 序列，以及最终仍返回失败。
4. **次数有界且只关心结果时，取消真实 sleep。** 例如存活探针始终失败的用例仍断言抛错与 FAILED 状态，只取消 30 次轮询之间的实际停顿。

因此，本次优化没有要求把生产环境的 30 秒等待缩成很短的超时。测试在自己的依赖边界控制时间，生产行为保持其原有预算。

需要注意：对依赖实际时间截止的 while 循环，仅把 sleep 替换成空函数可能造成忙等，应配套虚拟时钟。也不能只替换被测函数、再断言替身返回值；等待次数、顺序、失败状态和副作用应继续被验证。

本次补充验证了就绪/超时、进程清理与分组、防抖三类共 30 项测试，均通过；没有为写总结改动实现或新增测试。

## 四、并行：先处理共享资源，再选择 worker 数量

当前默认是 `-n 3 --dist loadgroup`。

`conftest.py` 中 27 个共享固定端口的测试文件进入 `real-ports` 同一分组，由同一个 worker 串行执行。其他测试按文件名分组，能够并发调度，同时保留文件内部的顺序执行方式。

这解决了 LWA 的实际限制：pytest worker 虽然分进程，但仍共享同一宿主机端口和服务。若把所有用例自由打散，多个 worker 会抢同一端口池，造成与产品无关的间歇失败。

历史上试过按 worker 平移端口池，但大量既有断言使用固定端口，改动范围大且易引入无关失败，最终采用资源分组。它是适合当前测试结构的折中，也意味着 real-ports 整组会成为耗时下限。

DEV-166 的 3 worker 与 8 worker 对照说明：当共享资源组已经主导总耗时，继续增加 worker 只能增加调度或资源成本，难以缩短最后一组的执行时间。当前 3 是已有测量支持的默认值，不是适用于所有机器与未来测试规模的永久最优值。

后续新增真实占用固定端口的文件，需要更新 `_REAL_PORT_FILES`。同组约束只在一次 pytest/xdist 运行内生效；两个独立测试会话之间仍可能争用宿主资源，不能把分组理解成跨会话全局锁。

## 五、隔离和清理是并行稳定的前提

共享夹具为测试创建临时 Workspace 和独立 registry；默认使用 builtin 网关，减少对宿主 Caddy admin 的接触。工作区选择等用例还隔离 XDG_CONFIG_HOME、LWA_WORKSPACE，并替换后台 manager 自启动。

Git 导入、更新测试使用临时 bare remote + clone，真实验证 Git 操作，但不依赖外部 GitHub 网络。小样例项目按需生成 zip，也让输入更可控。

进程清理有两层：测试夹具正常 teardown，以及 session 级兜底。

- http.server 正常残留按启动快照与结束差集清理。
- 对中断旧会话留下的 http.server，启动时按 pytest 路径标记及超过 3 小时的年龄阈值识别陈旧候选。
- manager/daemon 按本会话临时根归属过滤，另外处理工作区已经删除的历史孤儿。
- 无法确定年龄等情况保守跳过；不能仅凭占用“测试端口”就认定进程属于测试。
- 清理规则本身也有回归测试，包括生产路径排除、并发会话排除、目录边界及未知年龄。

这些规则降低了反复运行后端口池被污染的概率。年龄阈值仍属于启发式规则，进程归属与清理动作仍需要维护；不能将兜底清理替代正常 teardown。

## 六、验证深度与反馈速度共同管理

有代表性的做法是 Caddy 语义验证：生成配置后执行真实 `caddy adapt`，再对解析结果做路由语义断言。这比只检查配置字符串包含某一行更接近实际行为，同时不需要启动或重载宿主 Caddy。缺 Caddy 时会显式跳过，CI 配置安装固定版本启用这类检查。

它也有范围：路由模拟器只覆盖 LWA 使用的部分语义，不等于完整真实 HTTP 服务验收。真实 Docker 与应用 Eval 继续负责更高层的行为。

耗时约 35 秒的真实容器操作验收已改为显式启用，与其他 Docker 测试采用同类开关。这是调整日常与重型验证的执行频率，需要单独记录，不能包装成同样覆盖范围下纯粹的算法提速。

本次 Flask 路径问题也证明了限制：模板测试可以把与实现相同的错误假设断言为正确。应继续加入真实框架、真实解析器或业务行为的证据，尤其是持久化、启动命令和升级回滚等高影响边界。

## 七、本地与 CI 的一致性

`.github/workflows/ci.yml` 的 gate job 调用同一个 `bash tests/gate.sh`，安装 Python 3.13、开发依赖、MCP 可选依赖、pip 和固定版本 Caddy。相同分支的新运行会取消旧运行，减少失效任务排队。

mypy 四模块与覆盖率放在单独的 report job，当前 `continue-on-error: true`，没有覆盖率 fail-under。它们提供观察信息，目前不是硬门禁。report job 仍会再执行一次带覆盖率的测试，因此整个 CI workflow 的总耗时不能直接按本地 gate 的约百秒估计。

当前配置把反馈门槛和诊断报告区分开，便于逐步引入新检查；文档、PR 和发布结论也应准确说明哪些检查实际阻断、哪些只是报告。

## 八、建议继续沿用的日常流程

```bash
# 日常完整门禁：默认 3 worker
bash tests/gate.sh

# 定位问题：明确只跑选中子集
bash tests/gate.sh -k scanner -x

# 排查并行相关问题、查看慢用例
LWA_GATE_JOBS=1 bash tests/gate.sh --durations=20

# 在同一提交与环境上测量不同 worker，比较耗时和稳定性
LWA_GATE_JOBS=3 bash tests/gate.sh --durations=20

# 已准备好真实 Docker 环境时，显式运行重型验证
LWA_RUN_DOCKER_TESTS=1 LWA_GATE_JOBS=1 bash tests/gate.sh
```

之后的优化顺序建议为：查看慢用例 → 排查无关真实等待和环境访问 → 完善资源隔离/清理 → 再测并行数 → 连续复跑检查稳定性。性能记录同时保留提交、环境、用例数量、skip、worker、耗时及失败原因。

当前优先维护点包括：修复 BUG-913 的替身接口不一致；维护真实端口分组清单；在合适环境补 Docker/Eval；根据计时结果优化 real-ports 组内部的慢路径。历史三种 worker 测量、默认跳过规则与最新失败状态应分别记录。

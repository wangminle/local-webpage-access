## r1：发现问题比总通过率更有价值

r1 原报告记录 14 个基础部署成功单元、4 个标记为不支持的单元、2 个检测失败单元和 2 个阻断单元。14 个“成功”包含人工适配与重试，IT-Tools 的深链接断言当时仍失败，部分样本业务覆盖较浅。因此，该数字只保留为历史基础部署分类，不能解释为 14 个完整验收通过。

本轮集中暴露了识别与启动推断、包管理器与工作区上下文、更新重扫覆盖用户适配、失败更新的旧服务保护等问题。23 项发现（BUG-858～880）后续有回归测试与门禁记录；r1 环境清理后未原地复跑，不能用单元测试通过替代真实样本复验。r2 是独立的后续评测，其抽验也没有覆盖这 23 项缺陷的每个触发条件。

## r2：可运行样本与边界样本分开看

独立复核确认：**22/22 表示单元已执行；A01～A07、A09 共 8 个样本在两类环境中有初始部署及文件夹升级/回退的可用性证据。** 多项需要配置、手工初始化或补丁，不计作全部开箱即用。以下只归纳已留存证据，不把各样本最后一次成功覆盖此前失败。

| 样本 | macOS / Ubuntu 的共同观察 | 适配或证据限制 |
| --- | --- | --- |
| A01 2048 | 静态部署、文件夹切源、版本切换与回退有证据 | 直接部署基线；Git 默认分支内容相同不等于导入了冻结提交 |
| A02 IT-Tools | 构建、深链接、版本切换与回退得到支持 | 评测预先准备包管理器 shim，不能外推到仅安装 Corepack、没有 shim 的环境；没有连续探测证据可宣称零中断 |
| A03 Astro portfolio | 固定样例子目录可构建并切换版本 | 一类环境补充了符合项目要求的 Node 工具链；Git 整仓更新失败而旧产物继续服务，更新目标未达成 |
| A04 Flaskr | 配置额外挂载并初始化后，文章跨文件夹更新/回退保留 | 首次启动触发工厂命令引号问题，需补丁；默认 instance 持久化存在缺口，但归档不足以证明一次完整的“更新前有库、更新后丢库”事件 |
| A05 Uptime Kuma | 配置后可部署，监控与心跳数据有保留证据 | 触发 Node 数据目录问题；Ubuntu 的 Git 更新失败后旧版恢复且业务数据仍在。macOS 运行了上游 beta，但业务脚本未完整验证，不能算同等成功 |
| A06 linkding | 应用运行、书签落库与版本切换有证据 | 需要手工数据库迁移；部分环境需编译依赖。缺少迁移前缺表的直接日志，不能宣称两类环境均采证了同一缺表错误 |
| A07 Excalidraw | 正确选择主应用，构建、资产版本切换与回退有证据 | 需引擎兼容配置；一类环境发生下载错误及构建超时后重试成功，首次结果仍须保留 |
| A08 Homarr | 未建立可用部署 | 实际因静态路径找不到 HTML 失败，不能据此宣称已有可靠的 bun 不支持门禁 |
| A09 HedgeDoc | 在补齐配置与依赖后，两类环境均沿 Yarn 锁定路径构建运行 | Git monorepo 更新失败，旧版继续服务；同一笔记 URL 返回 200 只是较弱的数据证据，仍需正文/数据库对照 |
| A10 FastAPI Template | 导入待确认后仍可启动静态源码页 | 属于启动伪成功；不能计作部署通过或正确拒绝 |
| A11 Memos | Go 主服务识别警示得到验证 | start 仍能绕过待确认状态，API 不可用；导入识别成立不等于端到端拒绝成立 |

Git 更新时，`--ref` / `--subdir` 与 `--update` 的互斥是该冻结版本的能力边界。改为默认分支执行，会改变原先“更新到指定版本/子目录”的验收目标，须单独记结果。旧版仍可用说明失败保护有效，不能把目标更新失败改写成成功。

## 可以推广的工程结论

- **识别、进程存活、页面 200 与业务可用分别验收。** 待确认形态不能直接走静态启动；登录页正常也不能证明数据库已经初始化。
- **应用初始化与持久化是独立契约。** Flask instance、Node 数据目录、Django migrations 均需明确处理；不能因为某个教程需要初始化，就默认替所有应用执行数据库变更。
- **更新验证同时检查新版本和旧服务。** 内容、来源身份、数据、端口与别名分别核对；代码回退不等于数据库迁移可逆。
- **包管理器与工作区上下文不可丢失。** 保留锁文件、Yarn 配置与 patch、monorepo 子包关系；编译工具链与下载网络分别归因。
- **跨平台指纹需区分逻辑内容和归档字节。** 文件枚举顺序与权限元数据会影响打包 hash，不能只凭差异认定源码变化。
- **重试与缓存影响结果。** 首次失败、后续适配、重试成功应同时报告；构建耗时不能直接归因为 macOS 或 Ubuntu 性能。

Yarn Berry 依赖层修复获得两类环境真实构建支持，但 r1 的错误尾部不足以倒推唯一根因。r2 补工具链、换源或缓存后成功，只能反驳“Node 24 必然无法运行该 SQLite 依赖”的绝对判断，不能证明所有原失败都是同一网络问题。

## WSL：本机可达与 LAN 可达必须区分

该 Debian WSL2 NAT 专项中，WSL 内及 Windows localhost 均能访问静态演示页、CSS、JS，内容校验一致；独立 LAN 设备访问 Windows LAN 网页入口失败。只读观察发现网页端口没有相应 LAN 入站映射或监听。

LWA status / manifest / API 将 guest NAT 地址展示为访问入口，`lanAddressStale=false` 且来源为 `live`，doctor 的 `lan_url_stale` 为 OK。这里的“一致”不能证明 LAN 可达。doctor 整体还因缺少 Docker/Compose 为 fail，不能称整体全绿。防火墙规则读取被拒时，应报告未知，不能当作无规则或已放行。

对应 BUG-923 仍需修复。适配范围见 [跨 Windows / WSL 版本草案](../3-plans/2026-10-19-WSL跨Windows版本网络适配草案.md)：只读识别现有网络、准确展示地址范围及诊断原因，不内置第三方组网/注入工具，不自动修改 Windows 转发或防火墙。

## 尚不能声称通过的范围

- 原生 Debian、Docker Engine 26.1.5 / Compose 2.26.1 的完整部署矩阵；CHK-439 仍待专门验收。
- Windows 10/11 × WSL 软件包 2.x/3.x、NAT/mirrored 等组合的完整矩阵；WSL 软件包号不等于 WSL1/WSL2 架构号。
- 全部样本的外部浏览器交互、HTTPS 信任链、转发后来源身份与鉴权、真实重启恢复及零中断。
- 当前代码已经修复所有历史问题；本文记录冻结版本事实，最新状态与复验范围以 [任务台账](../../task-list.md) 为准。

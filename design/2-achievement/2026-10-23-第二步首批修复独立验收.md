## 验收发现

### BUG-984 / P1：pnpm 安装钉版后，容器构建与启动丢失 pnpm 入口

位置：`node_toolchain.py:257–261`，下游 `dockerfile_templates.py:297–298、343`。

安装从 `corepack enable && pnpm install` 改为 `corepack pnpm@8.15.9 install`，后者不会创建裸 `pnpm` shim。但生成 Dockerfile 后续仍是 `RUN pnpm run build`、`CMD ["pnpm", "run", "start"]`。适用于旧锁兜底和显式声明 pnpm 的新路径。

独立探针在真实 macOS shell 上隔离 PATH，仅保留 node/corepack：真实 pnpm 8.15.9 离线冻结安装 exit 0，下一条裸 pnpm 构建 exit 127（command not found）。另在真实 WSL 的缓存 `node:24-alpine` 镜像中离线执行工具检查，确认 Node 24.22.0、corepack 存在、pnpm 入口不存在，临时容器自动删除。前者为完整 shell 命令链复现，后者仅为容器工具分布确认；没有声称完整执行生成的 Dockerfile，也未把缓存 24.22.0 当成生成模板 24.22.1 的逐字验收。

需使安装、构建、嵌套脚本及启动使用同一包管理器入口和版本，或显式创建匹配 shim；增加完整链路回归，不能只断言安装字符串钉版正确。

### BUG-966 / P2：旧锁选择仍有确定性不兼容

位置：`node_toolchain.py:259–261`。

所有 `lockfileVersion <9` 均选择 pnpm 8.15.9。真实 pnpm 8.15.9 对空依赖包执行离线 frozen 安装：6.0 锁通过，5.3、5.4 均 exit 1，错误为 `ERR_PNPM_FROZEN_LOCKFILE_WITH_OUTDATED_LOCKFILE`。因此原 6.0 样本的安装修复成立，不能推广为全部旧锁兼容；需按实际锁格式选择可冻结读取的版本，并与 BUG-984 一起验证生命周期。

### BUG-967 / P2：兼容运行时未落实，镜像选择和范围解析仍有错误

位置：`hosting.py:456–471`、`dockerfile_templates.py:265–274`、`node_toolchain.py:343–344`。

- 宿主失配时无显式选择便追加 Yarn `--ignore-engines`，或覆盖项目 pnpm `engine-strict=true`。确实有 warning，不能称完全静默；但未提供兼容 Node，不能解决过旧 Node 缺少真实 API 的问题，也不满足既定 D3“按确认方案使用兼容运行时，不默认忽略”的边界。
- 镜像选择用 `major.0.0` 代替真实版本：`>=22.12.0 <23` 明确可使用合适的 22.x，却生成 `node:24.22.1-alpine`；`>=24.0.0 <24.10.0` 又因 24.0.0 满足而选实际不满足的 24.22.1。均由当前真实渲染函数复现，尚未执行业务镜像构建。
- caret 短范围 `^22.12` 对 22.15.0 被误判 False，本机 npm 自带 semver 实际判 True，会误触发兼容分支。

应以实际完整版本验证兼容性，选用兼容运行时或明确阻断；忽略约束只在显式选择下执行，并补上述边界。

# 安全边界紧急修复设计

## 目标

修复外部评审已确认的五个问题：monorepo npm workspace 包名命令注入、新端口分配忽略 bind-only 占用、`extraVolumes` 未按 Compose 短格式校验、`cap_add: ALL` 未告警，以及 Dockerfile 下载后执行审计覆盖面与文档承诺不一致。

## 设计决策

1. workspace 参数仍使用 npm `-w` 语义，但所有来自 `package.json.name` 或路径的值必须经 `shlex.quote` 渲染；不改变合法 scoped 包名的行为。
2. 新端口分配用 `is_port_in_use` 做独占 bind 探测；已登记的停止实例复用旧端口仍用 `is_port_listening`，保留 TIME_WAIT 下的稳定 URL 语义。
3. `container.extraVolumes` 只接受 `source:/absolute/container/path[:ro|rw]`；容器目标必须是 POSIX 绝对路径，源可为 Unix/Windows/变量路径。通过 JSON 字符串编码生成 YAML 标量，防止流式 mapping、注释或特殊标量改变结构。
4. `ALL` 纳入危险 capability 集，沿用现有 `warn` 分级，不在本次改变 Full Profile 的告警处置政策。
5. Dockerfile 审计聚焦“下载器将远程内容交给解释器执行”：覆盖管道以及 `&&`/`;` 串联，解释器覆盖 sh/bash/python/node/perl/ruby。普通构建钩子仍可使用 shell 操作符。文档明确这是高危模式门禁，不是任意源码沙箱。

## 错误处理与兼容

- 非法 `extraVolumes` 在生成 compose 前抛出带实例 ID 和条目的 `ValueError`，不写出半成品。
- 现有 `../data:/app/data` 等 LWA 管理挂载不经过 `extraVolumes` 校验，语义不变。
- Dockerfile 命中新高危模式仍使用现有 `pipe_to_shell` 稳定 code，避免不必要的 API 破坏。

## 验证

每项先增加会在现有实现上失败的回归测试，分别运行 Scanner、ports、compose、security 定向测试；最后运行全量 pytest、ruff、mypy 和 `task-list.md` 校验。

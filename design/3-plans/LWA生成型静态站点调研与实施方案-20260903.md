# LWA 生成型静态站点调研与实施方案

> **For Codex:** 下一阶段实施时，先使用 `executing-plans` skill，按本文任务拆解逐项执行并设置审查检查点。

**目标：** 为 LWA 增加受控的 `generated-static` 源码构建形态：自动识别少量已验证的静态站点生成器，在 Full 能力下无感完成一次性构建，并继续使用现有 `shared-static` 运行时在局域网提供访问。

**架构：** 生成器只参与构建，不成为长期运行时。源码先进入 LWA 工作区，随后由固定、可审计的预设在短生命周期构建容器中生成静态产物；产物验证通过后原子发布到实例 `public/`，最终复用现有静态网关、端口、路径别名、Gate-C 与生命周期能力。

**技术栈：** Python 3.13、Pydantic、SQLite Registry、现有 Build Queue、Docker/Compose 能力探测、Caddy/builtin 静态网关、Vue 管理页、pytest。

---

## 1. 文档性质与结论摘要

本文记录 2026-09-03 围绕 Hugo 及同类静态站点生成器完成的外部调研、与 LWA 的差异分析、云平台支持模式比较、方案讨论和最终产品决策，并作为下一阶段设计与实施输入。

最终结论如下：

1. LWA 应支持静态站点生成器的**工程源码**，而不只支持已经构建好的 HTML 部署包。
2. 新源码形态命名为 `generated-static`，构建后仍使用现有 `shared-static` 运行时。
3. 采用“**通用协议 + 少量验证过的框架预设**”，第一批预设为 Hugo、Hexo、MkDocs、Jekyll、Eleventy。
4. 不允许 Scanner 根据仓库内容任意拼接或执行 Shell 命令；第一阶段也不提供任意自定义构建命令入口。
5. 构建在固定镜像的短生命周期容器内完成，不污染宿主机；构建完成后不保留生成器服务进程。
6. **Full 能力已就绪时，高置信度命中预设后自动构建、验证并运行，不要求用户确认，也不向普通用户解释 Docker/Hugo 细节。**
7. **Default 能力或构建能力不足时，不尝试危险降级；实例保留为可恢复状态，并用通俗语言提示启用完整模式或导入已构建站点。**
8. 更新构建失败时继续服务上一成功版本；只有新产物通过验证后才原子切换。
9. 用户可见术语尽量接近 Cloudflare Pages、Vercel、阿里云 ESA Pages、腾讯云 EdgeOne Makers：Framework Preset、Root Directory、Build Command、Output Directory。

## 2. 调研起点：Hugo 是什么

调研从微信公众号文章《Hugo搭建静态网站教程》开始。文章介绍的主角仓库为 `gohugoio/hugo`：

- 输入主要是 Markdown 内容、模板、主题、站点配置和静态资源；
- 本地使用开发服务器预览；
- 执行构建后默认生成 `public/`；
- 最终产物为不依赖后端服务的 HTML、CSS、JavaScript 和资源文件；
- 典型用途包括博客、文档站、作品集和内容门户。

官方资料进一步表明，Hugo 不只是 Markdown 转 HTML 工具，还包含模板、多语言、taxonomy、Modules、图片处理、CSS/JS/Sass/Tailwind 管线等能力。

相关资料：

- 微信文章：[Hugo搭建静态网站教程](https://mp.weixin.qq.com/s/p234rfSRBZSfrrx6-8Lnhg)
- Hugo 仓库：[gohugoio/hugo](https://github.com/gohugoio/hugo)
- Hugo 文档：[Hugo Documentation](https://gohugo.io/documentation/)
- Hugo 托管与部署：[Host and deploy](https://gohugo.io/host-and-deploy/)

### 2.1 Hugo 与 LWA 不是竞品

二者位于不同层级：

| 维度 | Hugo | LWA |
| --- | --- | --- |
| 核心任务 | 从内容、模板和资源生成网站 | 导入、识别、构建、运行和管理 Web 项目 |
| 输入 | Markdown、模板、主题、配置 | ZIP、本机目录、GitHub 仓库 |
| 输出 | 静态部署产物 | 局域网可访问的静态或容器实例 |
| 内容能力 | 分类、标签、多语言、主题、短代码 | 不承担 CMS 和内容建模 |
| 运维能力 | 主要负责构建 | 端口、网关、别名、日志、自启、自愈、诊断、安全门禁 |

二者更适合组成上下游：

```text
Markdown + 主题/模板
        ↓ Hugo 等生成器
HTML + CSS + JS 静态产物
        ↓ LWA
局域网地址 + 网关 + 生命周期管理
```

## 3. 同类生态是否值得支持

调研确认，静态站点生成器不是单个小众工具，而是成熟且规模较大的类别。代表项目包括：

| 工具 | 主要环境 | 典型场景 | 默认/常见产物目录 |
| --- | --- | --- | --- |
| Hugo | Go/单二进制 | 博客、内容站、文档、多语言站点 | `public/` |
| Hexo | Node.js | 博客，中文主题生态较丰富 | `public/` |
| Jekyll | Ruby | 博客、GitHub Pages 项目站 | `_site/` |
| MkDocs | Python | 技术文档、知识库 | `site/` |
| Eleventy | Node.js | 灵活内容站、营销站 | `_site/` |
| VitePress | Node.js/Vue | 技术文档 | `.vitepress/dist/` |
| Docusaurus | Node.js/React | 版本化大型文档 | `build/` |
| Astro | Node.js | 现代内容站和营销站 | `dist/` |

这类工具普遍形成了四层生态：

1. Theme：布局、样式和页面结构；
2. Starter：主题、示例内容、搜索、SEO、评论和部署配置的完整起始仓库；
3. Plugin/Module：Markdown 扩展、图片、搜索、数学公式、RSS、多语言等；
4. CI/CD Recipe：Git 提交后执行安装、构建并发布指定输出目录。

参考资料：

- [Jamstack Static Site Generators](https://jamstack.org/generators/)
- [Hugo Themes](https://themes.gohugo.io/)
- [Hexo Themes](https://hexo.io/docs/themes)
- [Jekyll Themes](https://jekyllrb.com/docs/themes/)
- [MkDocs Choosing Your Theme](https://www.mkdocs.org/user-guide/choosing-your-theme/)

## 4. 云平台支持方式调研

### 4.1 Cloudflare Pages

Cloudflare Pages 为大量静态和前端框架提供专门指南，覆盖 Hugo、Hexo、Jekyll、MkDocs、Eleventy、Astro、Docusaurus、VitePress 等。其共性模型是：

```text
Git 仓库
→ 框架预设
→ 安装/构建命令
→ 输出目录
→ 边缘静态托管
```

参考：[Cloudflare Pages Framework Guides](https://developers.cloudflare.com/pages/framework-guides/)

### 4.2 Vercel

Vercel 提供 Supported Frameworks、Framework Preset 和模板市场。导入仓库后自动设置安装命令、构建命令和输出目录；未识别框架可选择 Other 并自定义。

Vercel 更值得借鉴的架构是 Build Output API：框架只需生成约定的 `.vercel/output/` 结构，平台即可理解静态文件、函数、路由和缓存，不必深入耦合框架内部实现。

参考资料：

- [Frameworks on Vercel](https://vercel.com/docs/frameworks)
- [Configuring a Build](https://vercel.com/docs/builds/configure-a-build)
- [Build Output API](https://vercel.com/docs/build-output-api)

### 4.3 阿里云 ESA 函数和 Pages

阿里云 ESA Pages 已形成接近 Cloudflare Pages 的 Git、自动构建和边缘分发流程，并为 Vite+React、Vite+Vue、Next.js 静态导出、Astro、Nuxt、Gatsby、Svelte 等列出默认构建命令和静态资源目录。

当前公开框架预设更偏现代 JavaScript 生态；传统的 Go/Ruby/Python 生成器是否能直接源码零配置构建，需要结合具体构建环境判断，不能一概视为原生支持。

参考资料：

- [阿里云 Pages 前端框架说明](https://help.aliyun.com/zh/edge-security-acceleration/esa/user-guide/framework-guide)
- [什么是函数和 Pages](https://help.aliyun.com/zh/edge-security-acceleration/esa/user-guide/what-is-functions-and-pages/)

### 4.4 腾讯云 EdgeOne Makers 与 CloudBase

腾讯 EdgeOne Pages 已升级为 EdgeOne Makers。其框架指南覆盖 Next.js、React、Vue、Nuxt、Astro、Docusaurus、Gatsby、Hexo、Svelte 等，并已为 Hugo 提供专门原生适配：自动识别、Hugo Extended、版本指定、构建缓存、自动构建和持续部署。

CloudBase 静态网站托管则提供本地上传、模板部署、Git 仓库部署、Node 构建命令、输出目录和缓存，更接近“静态托管 + 通用 Node 构建”。

参考资料：

- [EdgeOne Makers Framework Guide](https://edgeone.ai/document/160427672961769472)
- [EdgeOne Makers Hugo](https://cloud.tencent.com/document/product/1552/130380)
- [CloudBase 静态网站托管](https://cloud.tencent.com/document/product/876/46900)

### 4.5 云平台调研归纳

四类平台虽覆盖范围不同，但产品抽象高度一致：

1. 以 Framework Preset 自动填充常用配置；
2. 以 Root Directory、Build Command、Output Directory 描述构建契约；
3. 构建和最终运行/托管分离；
4. 静态产物进入统一托管层；
5. 未满足构建条件时给出清晰配置或能力提示。

LWA 应借鉴这套通用模型，而不是复制各云平台的复杂 Serverless、边缘函数和多租户能力。

## 5. LWA 当前能力与缺口

LWA 当前已经支持两条静态路径：

1. 已存在 HTML 的纯静态项目：复制到实例 `public/` 后由共享静态网关托管；
2. Node 前端 SPA：安装依赖、运行 `npm run build`、查找 `dist/build/out`，再进入共享静态托管。

当前缺口是：Hugo、MkDocs、Jekyll 等工程源码在构建前通常没有可直接托管的 HTML，也可能没有 LWA 当前识别的 Node/Python Web 信号，因此会落入 `pending`。即使已有 `EntryConfig.buildOutputDir`、构建队列、日志和 Gate-C，也缺少：

- `generated-static` 这一明确源码形态；
- 生成器预设注册表；
- 与预设绑定的短生命周期构建环境；
- Full/Default 的能力分层提示；
- 新旧静态产物原子发布和失败保旧策略；
- 生成器构建缓存与相关诊断信息。

现有可复用组件包括：

- `scanner.py` / `candidate_generator.py`：检测与候选生成；
- `models.py`：manifest 和 entry/build 输出信息；
- `build_queue.py` / `build_process.py`：构建排队、进程和取消；
- `hosting.py`：前端构建、输出目录识别、静态发布；
- `capability.py` / `preflight.py`：Full 能力与预检；
- `static_gateway.py` / `gateway_service.py`：最终静态托管；
- `verification_config.py` / Gate-C：启动后实证；
- `manager_api.py` 与管理页：状态和操作反馈。

## 6. 讨论过的方案与取舍

### 6.1 方案 A：只接受已构建静态包

LWA 只接受 `public/`、`site/`、`_site/`、`dist/` 等已经包含 HTML 的目录。

优点：最轻、安全边界最简单，现有功能已经基本覆盖。

缺点：用户仍需理解并安装 Hugo/Node/Python/Ruby，手工构建后再判断该导入哪个目录；没有实现“导入工程源码即可在局域网预览”的核心体验。

结论：继续保留，作为 Default 档和能力不足时的退路，但不足以构成新功能。

### 6.2 方案 B：通用协议 + 少量受控预设

LWA 识别有限的高置信度生成器项目，通过固定镜像和固定构建规则生成静态产物，再复用现有静态托管。

优点：用户体验接近主流 Pages 平台；框架覆盖可逐步增加；构建与运行解耦；安全和可测试边界清晰。

缺点：需要维护预设、镜像版本、构建缓存和兼容性测试。

结论：**采用。**

### 6.3 方案 C：开放任意自定义构建命令

用户或 Scanner 可填任意 `buildCommand`，由 LWA 执行。

优点：兼容性最大，未知生成器也能接入。

缺点：命令注入和供应链风险高；宿主/容器边界复杂；错误提示与可复现性差；容易把 LWA 扩张成通用 CI 平台。

结论：第一阶段不做。后续如开放，也必须是显式高级功能、可信项目限定，并与预设模式分离。

### 6.4 构建环境：宿主工具链还是短生命周期容器

讨论了三种执行方式：

| 方式 | 优点 | 风险/成本 | 结论 |
| --- | --- | --- | --- |
| 宿主安装 Hugo/Node/Python/Ruby | 启动快、实现直观 | 污染宿主、版本漂移、跨平台维护复杂 | 不采用为默认方案 |
| 固定短生命周期构建容器 | 可复现、不污染宿主、易审计 | 首次拉镜像、需要 Full/Docker | **采用** |
| 任意用户命令 | 灵活 | 安全边界失控 | 第一阶段不做 |

## 7. 最终产品定义

### 7.1 两个正交维度

```text
源码形态：generated-static
        ↓ 一次性构建
运行形态：shared-static
```

`generated-static` 不是新长期 runtime，而是进入 `shared-static` 前的一段受控构建流程。

### 7.2 用户体验原则

目标用户不需要理解 Docker、Hugo 镜像或构建容器：

- Full 已就绪且预设高置信度命中：自动导入、自动构建、自动验证、自动运行，直接给出局域网地址；
- Default 或 Full 未就绪：不执行源码构建，给出通俗提示和两条明确出路；
- 技术细节只进入高级详情、构建日志和诊断，不成为普通用户必须回答的问题；
- 不为“安全”增加无必要确认框。安全通过受控预设、容器边界和预检实现。

## 8. 通用协议与用户可见字段

用户术语尽量与 Cloudflare/Vercel/EdgeOne 一致：

```yaml
form: generated-static
frameworkPreset: hugo
rootDirectory: .
buildCommand: hugo --minify
outputDirectory: public
```

第一阶段字段语义：

| 字段 | 来源 | 用户权限 | 说明 |
| --- | --- | --- | --- |
| `form` | Scanner | 只读 | 固定为 `generated-static` |
| `frameworkPreset` | Scanner/人工选择 | 可从受支持列表修正 | Hugo/Hexo/MkDocs/Jekyll/Eleventy |
| `rootDirectory` | Scanner | 可在 `current/` 内修正 | Monorepo 或子目录项目使用 |
| `buildCommand` | 预设 | 普通界面只读 | 不接受项目内容拼接任意 Shell |
| `outputDirectory` | 预设/安全修正 | 可在构建工作区内修正 | 必须经过 containment 与产物验证 |

内部模型可将这些字段归入结构化 `GeneratorBuildSpec`，并额外记录：

- 预设版本；
- 构建器镜像和版本；
- 缓存目录；
- 检测证据；
- 最近构建状态、开始/完成时间、日志路径；
- 最近成功产物指纹；
- 失败时保留的上一成功版本信息。

## 9. 首批框架预设

### 9.1 预设共同约束

每个预设必须声明：

1. 高置信度检测信号；
2. 信号冲突时的优先级与拒绝条件；
3. 固定构建镜像/版本策略；
4. 固定安装和构建入口；
5. 默认根目录与输出目录；
6. 可持久化缓存目录；
7. 最低产物验证要求；
8. 面向用户的缺能力和失败提示。

### 9.2 建议的第一批矩阵

| 预设 | 高置信度信号 | 展示构建命令 | 默认输出目录 | 主要歧义 |
| --- | --- | --- | --- | --- |
| Hugo | `hugo.toml/yaml/json`，或 Hugo `config/` 配合 `content/` | `hugo --minify` | `public/` | 主题可能附带 Node 工具链 |
| Hexo | `_config.yml` + `package.json` 中 Hexo 依赖/脚本 | `hexo generate` | `public/` | `_config.yml` 与 Jekyll 命名冲突 |
| MkDocs | `mkdocs.yml/yaml` + 文档目录 | `mkdocs build` | `site/` | 插件与主题是 Python 依赖 |
| Jekyll | `_config.yml` + `Gemfile`/Jekyll 依赖或 `_posts/` | `bundle exec jekyll build` | `_site/` | Ruby/Gem/原生扩展兼容 |
| Eleventy | `eleventy.config.*`/`.eleventy.js` + `@11ty/eleventy` | `npx @11ty/eleventy` | `_site/` | 配置可自定义输出目录 |

上述命令用于用户展示；容器内部可将真实目的目录重定向到受控 staging 目录，避免直接覆盖线上 `public/`。

## 10. Full 与 Default 能力分层

### 10.1 Full 已就绪

满足以下条件时自动执行，不弹确认：

- Scanner 高置信度命中唯一受支持预设；
- Full capability report 表明 Docker/构建队列/静态网关等所需能力可用；
- root/output 路径通过边界校验；
- 没有生成器冲突或必须人工选择的版本冲突。

用户看到的是普通导入进度：

```text
正在准备网站
→ 正在生成静态页面
→ 正在检查页面
→ 已可访问
```

高级详情才展示：Framework Preset、Build Command、Output Directory、镜像、构建日志。

### 10.2 Default 或构建能力不足

导入结果不得笼统显示“无法识别”，应显示：

> 已识别为可生成静态网站的项目。当前模式只能直接预览已经生成的网站文件；启用完整模式后，LWA 可以自动生成并运行。你也可以在其他环境生成网站后，导入输出目录。

详细操作区可给出：

- “启用完整模式”的产品级动作或对应 CLI；
- 当前缺失能力的高级详情；
- 该预设通常生成的目录，例如 Hugo 的 `public/`、MkDocs 的 `site/`；
- 保留实例与来源信息，能力补齐后可继续构建，不要求重新导入。

不得在主要提示中要求用户理解“Docker 未安装”“Hugo 镜像不存在”等内部术语；这些内容放入诊断详情。

### 10.3 无高置信度预设

- 保持 `pending`；
- 展示已有检测证据；
- 允许从五个支持预设中人工选择；
- 允许修正 `rootDirectory` 和安全范围内的 `outputDirectory`；
- 不提供任意 Shell 输入框；
- 允许改为导入已构建静态目录。

## 11. 构建与发布数据流

```text
ZIP / 文件夹 / GitHub
        ↓ 复用现有导入安全管线
apps/<id>/current/
        ↓ Scanner + preset registry
generated-static manifest
        ↓ Full 能力检查
现有 build queue（默认并发 1）
        ↓
apps/<id>/build-staging/<build-id>/work/
        ↓ 短生命周期非 root 构建容器
apps/<id>/build-staging/<build-id>/output/
        ↓ 静态产物验证
候选 public
        ↓ 原子发布/回滚
apps/<id>/public/
        ↓
现有 shared-static + Gate-C
        ↓
局域网 URL / 路径别名
```

建议不要直接在 `current/` 安装依赖或生成产物。为每次构建创建工作副本或受控构建上下文，原因是：

- 保持 `current/` 作为导入源码事实副本；
- 防止 `node_modules/`、生成文件污染源码指纹和 source staleness；
- 构建取消和失败时可直接清理；
- 新旧构建互不覆盖，便于原子发布。

容器挂载原则：

- 不挂载用户原始关联目录；
- 不挂载 Docker socket；
- 工作目录和输出目录只允许位于本次 staging；
- 缓存只挂载到实例专用缓存目录；
- 以非 root 身份运行；
- 资源限制和构建并发沿用 LWA 小主机策略；
- 构建网络访问应明确记录，不能把构建容器宣传成安全沙箱。

## 12. 产物验证与原子切换

新产物成为线上 `public/` 前至少验证：

1. 输出目录真实存在且位于本次 staging 内；
2. 不接受路径逃逸、越界符号链接和设备文件；
3. 存在 `index.html` 或被 LWA 明确支持的入口；
4. 文件数、单文件大小、总大小符合配置上限；
5. 首页引用的关键本地资源存在；
6. base URL/base path 与路径别名风险经过现有或扩展 Gate-A 检查；
7. 候选产物先在临时入口完成基本 HTTP 探测；
8. 原子切换后再执行现有 Gate-C 实证。

发布策略：

- 首次构建成功：候选目录原子改名/切换为 `public/`；
- 更新构建成功：保留旧目录到新版本 Gate-C 通过，再回收旧版本；
- 更新构建失败：继续服务旧 `public/`，实例显示 `degraded/update_failed`，不制造停站；
- 首次构建失败：状态为 `build_failed`，保留日志和源码，不伪装为可运行；
- 发布切换失败：恢复旧目录和旧网关状态，并记录失败阶段。

## 13. 状态、日志和管理页

建议复用现有状态机并增加必要的阶段信息：

```text
importing
→ detected/generated-static
→ queued
→ building
→ verifying
→ running
```

失败状态/原因至少区分：

- `capability_required`：Default 或 Full 未准备好；
- `preset_conflict`：同时命中或证据不足；
- `builder_prepare_failed`：镜像或依赖环境准备失败；
- `build_failed`：生成器命令失败；
- `output_missing`：命令成功但没有合格产物；
- `artifact_rejected`：产物违反边界或限制；
- `verification_failed`：静态产物可发布性验证失败；
- `publish_failed`：原子切换或网关更新失败。

管理页建议显示：

```text
框架预设      Hugo
源码类型      生成型静态站点
构建命令      hugo --minify
产物目录      public/
运行方式      共享静态网关
最近构建      成功 · <时间>
```

“一次性容器”“镜像摘要”等只进入高级详情。

## 14. 安全边界

第一阶段明确坚持：

- 不在用户源目录就地运行；
- 不因项目包含某个脚本就自动执行该脚本；
- 不允许项目覆盖预设构建命令；
- 不允许 root/output/cache 路径逃逸实例目录；
- 不把源仓库自带 Dockerfile 当作构建器；
- 不挂载 Docker socket、宿主敏感目录或其他实例目录；
- 不把短生命周期构建容器描述为强隔离沙箱；
- 构建依赖与主题仍属于不可信供应链，只导入可信项目；
- 镜像版本必须固定并纳入 `lwa doctor`/版本新鲜度检查；
- 构建日志不得泄露业务密钥或管理页 token；
- 第一期不自动向构建环境注入应用 `.env.local` 或业务密钥。

## 15. 非目标

第一阶段不做：

- Hugo/Hexo/Jekyll/MkDocs/Eleventy 的主题管理器；
- Markdown 编辑器、CMS、标签/分类管理；
- 长期运行 `hugo server` 等开发服务器；
- 在用户关联源码目录 watchdog 热构建；
- 任意自定义 Shell 构建命令；
- 模拟 Cloudflare/Vercel 的边缘函数、Serverless、多租户和 Preview Branch；
- 为所有静态生成器提供无限兼容承诺；
- 自动修改用户仓库配置来修复主题或插件问题。

## 16. 与现有 LWA 行为的兼容关系

- 已构建静态包仍按现有 `static/shared-static` 路径处理；
- Node SPA 仍按现有 `frontend-static` 路径处理，不强制迁移；
- `generated-static` 只在更强生成器证据存在时抢占，避免把普通 Node 项目误判为 Hexo/Eleventy；
- 现有 ZIP、文件夹、GitHub 三种来源汇入同一导入管线；
- `import --update`、`rebuild --sync` 和 Git 更新必须保留 preset 与用户安全修正字段；
- 最终端口、路径别名、浏览量、日志、remove、recover、autostart 等仍复用现有静态实例能力。

## 18. 验收标准

功能完成必须同时满足：

1. 五个最小示例均能被唯一正确识别；
2. Full 就绪时，用户导入后无需理解或确认构建技术即可得到可访问 URL；
3. Default 时不执行构建，提示准确且可恢复；
4. 构建不在用户源目录运行，不污染 `current/`；
5. 构建命令、镜像、默认输出均来自受控预设；
6. 更新失败不会使上一成功站点下线；
7. `outputDirectory`、符号链接和挂载均不能逃逸实例边界；
8. 生成器容器构建后退出，线上无生成器常驻进程；
9. 最终实例仍可使用现有端口、别名、浏览量、日志、remove、recover 和 autostart；
10. CLI、JSON API、管理页和文档对状态与提示的描述一致；
11. 全量自动化门禁与至少一轮真实 Docker 集成验证通过。

## 19. 推荐实施顺序

建议分三批落地：

### 第一批：协议闭环

- 数据模型；
- 预设注册表；
- Scanner；
- Full/Default 路由；
- 先用 Hugo + 一个 Node 生成器跑通端到端。

### 第二批：可靠发布

- 五类预设补齐；
- 构建队列与取消；
- staging、产物校验、原子发布、失败保旧；
- 管理页和错误提示。

### 第三批：产品化门禁

- doctor、缓存、源更新；
- 文档与 Skills；
- 完整验收矩阵；
- 真实小主机资源和首次拉镜像体验验证。

不建议一次性并行实现五类生成器全部细节。先验证通用协议确实能让 Hugo 和 Hexo/Eleventy 共用一条构建发布管线，再扩充其他预设，可降低把预设差异错误写进核心流程的风险。

## 20. 最终决策记录

本轮讨论最终确认：

- 用户所需不是只托管生成器已经产出的部署包，而是导入生成器工程源码后，由 LWA 的通用框架自动转换为可在局域网预览的站点；
- LWA 要接近 Cloudflare Pages、Vercel、阿里云 ESA Pages、腾讯 EdgeOne Makers 的标准构建术语和工作流；
- LWA 仍保持轻量，不承担主题、CMS、编辑器和任意 CI；
- 采用 `generated-static → 一次性构建 → shared-static`；
- 第一批支持 Hugo、Hexo、MkDocs、Jekyll、Eleventy；
- 采用短生命周期构建容器和受控预设；
- Full 状态下自动完成，不要求用户点击“构建并部署”；
- Default 状态下明确提示能力不足及两条出路；
- 下一阶段以本文为设计基线进入实施计划执行和代码开发。

## 1. IMP-029 — 资源采集接入周期任务：补资源列与内存趋势监控

> **状态**：需求触发后重新论证（P2，PLN-044）。`stats.collect_and_store()` 与 `resources` 表已有基础，但尚未证明家庭服务器场景需要持续采样与趋势存储。

### 1.1 需求

- 为 running 的容器实例周期采集 CPU 与内存并写入已有 `resources` 表。
- 管理页资源列读取最近一次采样；可选提供近 N 次内存趋势供泄漏排查。
- shared-static 由 Caddy 统一伺服、无独立进程，资源列保持 `—`。

### 1.2 关键决策（立项前必须拍板）

| 编号 | 决策点 | 待确认内容 |
| --- | --- | --- |
| **029.a** | 真实需求 | 明确哪些实例、哪类事故需要长期资源趋势，而不是一次性 `docker stats`/`ps` |
| **029.b** | 采集进程归属 | daemon 主循环、manager 后台任务或独立调度；不得形成两个采集者 |
| **029.c** | 频率与预算 | 默认间隔、单轮超时、实例数上限及对低性能家庭服务器的 CPU/IO 预算 |
| **029.d** | 数据保留 | 保留窗口、聚合/清理策略、数据库增长上限 |
| **029.e** | 展示边界 | 仅最近值，还是详情页/CLI 趋势；不在本项内扩张成完整 APM |

### 1.3 现状触点

| 触点 | 现状 |
| --- | --- |
| `stats.collect_and_store()` | 已能采集实例 CPU/内存并写入 registry `resources` 表，但没有周期调用者 |
| 管理页资源列 | 已读取 `lastMemoryBytes/lastCpuPercent`，有数据后可直接展示 |
| 容器采集 | 可复用 `docker stats`；超时或容器不存在时应跳过单实例 |
| shared-static | 无独立进程，不采集实例级 CPU/内存 |

## 2. IMP-048 — ZIP 包模式 ↔ 文件夹源模式自由转换

> **状态**：需求触发后重新论证（PLN-031）。只有出现明确双向来源转换场景，并补齐数据兼容、迁移和失败回滚方案后才立项；`sourceKind` 预留不构成实施承诺。

### 2.1 需求

- ZIP 源实例可显式绑定本机文件夹，之后使用文件夹更新。
- 文件夹源实例可显式解除源目录依赖，回到 ZIP/inbox 更新路径。
- 不做自动双向同步，不与既有导入/更新管线混淆。

### 2.2 关键决策（立项前必须拍板）

1. 转换是否完整保留 `data/`、别名、端口、desiredState 与 git/folder 身份字段。
2. 转换后“更新”入口、CLI 参数和管理页操作如何切换且不误导。
3. 源目录消失时是否允许自动降级；默认倾向 fail-closed 并要求用户确认。
4. 转换事务如何快照、失败回滚及恢复旧来源身份。

### 2.3 现状触点

- IMP-047 已提供 folder 导入/更新；既有 ZIP 管线继续独立存在。
- manifest 已有 `sourceKind` 等身份基础，但没有转换状态机或 UI。
- git 源不纳入本 IMP 的 ZIP ↔ folder 转换。

| **048.02** | 迁移/回滚契约 | 来源身份、数据、别名、端口和事件链均可恢复 |
| **048.03** | importer 原子转换 API | dry-run、锁、快照、失败恢复闭环 |
| **048.04** | CLI/API/管理页入口 | 转换需显式确认，更新入口与新身份一致 |

## 4. IMP-050 — 生产 CLI 与工作区解耦安装

> **状态**：需求触发后重新论证（PLN-033；原合集 Task 11/P2）。多工作区或正式部署形成持续需求后再立项。

### 4.1 需求

安装和升级 `lwa` CLI 的 Python/venv/入口脚本与具体工作区目录解耦，避免 editable 安装或解释器路径钉死旧工作区，导致 relocate 后 CLI、自启和 update 难以恢复。

### 4.2 关键决策（待拍板）

| 编号 | 决策点 | 倾向 |
| --- | --- | --- |
| **050.a** | 推荐布局 | 用户级或全局 venv + `lwa --workspace`/环境变量指向工作区 |
| **050.b** | 与 autostart | 单元固定 CLI 解释器，工作区仅作为显式参数或环境变量 |
| **050.c** | 与开发模式 | 开发机保留 editable；生产安装、升级与回滚采用稳定通道 |
| **050.d** | 多工作区 | 明确默认工作区选择、并发操作和状态隔离，不自动合并实例列表 |

### 4.3 现状触点

- 当前 clone + editable 安装与工作区目录耦合，简单单工作区场景成本最低。
- autostart 单元和 update continuation 都依赖稳定解释器及明确工作区。
- `workspace relocate` 可修复工作区数据，但不等价于迁移 CLI 安装本身。

## 5. IMP-063.13 — 一键 GitHub 更新通道实机验收

> **状态**：待实机验收（CHK-285）。IMP-063 的 063.01～12 与 DEV-119 已完成；本节只验证真实代理、真实远端、跨版本升级和新解释器 handoff，不重复实现功能。

### 5.1 验收目标

在事故形态环境中证明一条 `lwa update` 能完成远端探测、安全快进、pip、新解释器 continuation、Runtime 后半段和服务恢复，并验证离线降级及并发锁语义。

### 5.2 环境前提

- clone/editable 安装，当前版本落后远端至少两个版本。
- 真实 GitHub 远端；`https_proxy` 指向 mihomo 等真实代理。
- 可观察父进程与 continuation 使用的新解释器版本及最终报告。
- 使用隔离工作区或可恢复的非关键机器，先记录当前 HEAD、服务状态和配置备份。

### 5.3 实机清单

| 项 | 手工步骤 | 通过标准 |
| --- | --- | --- |
| A | 代理环境执行一条 `lwa update` | `sourceUpdate ok`；无人工 git；Runtime 由 continuation 完成且版本一致 |
| B | 已是最新时再次执行 | `sourceUpdate skipped（已是最新）`，其余 Runtime 步骤照旧 |
| C | 断开代理/网络后执行 | `sourceUpdate warning`，本地代码继续完成 Runtime，退出码 0 |
| D | 未 init 工作区目录执行 `lwa update --check` | 输出 SourceCheckReport；不改工作树与 Runtime；退出码 0/1/2 语义正确 |
| E | kill 一个 enabled 服务后执行 update | 报告标明意外未运行并恢复，accessReview 转绿 |
| F | 两个 update 并发 | 后者 fail-fast 报更新锁占用，不触碰 pip、进程和 registry |

### 5.4 证据记录

- 验收日期、主机/系统、代理形态、oldHead/newHead 与版本跨度。
- `sourceUpdate`、continuation、Runtime、服务 reconcile 和最终退出码摘要。
- A～F 每项结果；失败时记录日志路径、残余状态和恢复操作。
- 将最终证据回填 `docs/acceptance-checklist.md` 与 CHK-285。

### 5.5 失败处理

- 任一失败先停止验收，不自动 reset/rebase/stash；按 update 报告恢复链处理。
- 若发现代码缺陷，另开 BUG 并保留复现证据；CHK-285 保持待办或进行中。
- 环境不满足版本跨度或真实代理条件时不得以本地 bare remote/直连结果替代。

### 5.6 验收标准

- A～F 均有可审计证据且全部通过。
- 新进程版本、source report 与 Runtime 报告一致。
- 失败/离线/并发路径不产生未声明写入或服务状态污染。

### 6.1 新候选进入规则

- 新功能先给出真实场景、用户价值、兼容边界、迁移/回滚和完成证据，再分配新 IMP 编号。
- 不把 GitHub Issue、一次性运维异常或历史“不做”项直接升级为功能。
- 需求触发型候选在未满足启动条件时保持待办，不为清空月度表而开发或关闭。

## 5. IMP-063.13 — 一键 GitHub 更新通道实机验收

> **状态**：待实机验收（CHK-285）。IMP-063 的 063.01～12 与 DEV-119 已完成；本节只验证真实代理、真实远端、跨版本升级和新解释器 handoff，不重复实现功能。

### 5.1 验收目标

在事故形态环境中证明一条 `lwa update` 能完成远端探测、安全快进、pip、新解释器 continuation、Runtime 后半段和服务恢复，并验证离线降级及并发锁语义。

### 5.2 环境前提

- clone/editable 安装，当前版本落后远端至少两个版本。
- 真实 GitHub 远端；`https_proxy` 指向 mihomo 等真实代理。
- 可观察父进程与 continuation 使用的新解释器版本及最终报告。
- 使用隔离工作区或可恢复的非关键机器，先记录当前 HEAD、服务状态和配置备份。

### 5.3 实机清单

| 项 | 手工步骤 | 通过标准 |
| --- | --- | --- |
| A | 代理环境执行一条 `lwa update` | `sourceUpdate ok`；无人工 git；Runtime 由 continuation 完成且版本一致 |
| B | 已是最新时再次执行 | `sourceUpdate skipped（已是最新）`，其余 Runtime 步骤照旧 |
| C | 断开代理/网络后执行 | `sourceUpdate warning`，本地代码继续完成 Runtime，退出码 0 |
| D | 未 init 工作区目录执行 `lwa update --check` | 输出 SourceCheckReport；不改工作树与 Runtime；退出码 0/1/2 语义正确 |
| E | kill 一个 enabled 服务后执行 update | 报告标明意外未运行并恢复，accessReview 转绿 |
| F | 两个 update 并发 | 后者 fail-fast 报更新锁占用，不触碰 pip、进程和 registry |

### 5.4 证据记录

- 验收日期、主机/系统、代理形态、oldHead/newHead 与版本跨度。
- `sourceUpdate`、continuation、Runtime、服务 reconcile 和最终退出码摘要。
- A～F 每项结果；失败时记录日志路径、残余状态和恢复操作。
- 将最终证据回填 `docs/acceptance-checklist.md` 与 CHK-285。

### 5.5 失败处理

- 任一失败先停止验收，不自动 reset/rebase/stash；按 update 报告恢复链处理。
- 若发现代码缺陷，另开 BUG 并保留复现证据；CHK-285 保持待办或进行中。
- 环境不满足版本跨度或真实代理条件时不得以本地 bare remote/直连结果替代。

### 5.6 验收标准

- A～F 均有可审计证据且全部通过。
- 新进程版本、source report 与 Runtime 报告一致。
- 失败/离线/并发路径不产生未声明写入或服务状态污染。

## 6. IMP-066 — Flask/Django 后端使用生产服务器模板

> **状态**：方案 B 已拍板，规划完成（PLN-046），待实施时另开 DEV。来源：2026-09-02 安全评审复核第 9 条。Flask/Django 当前默认生成框架自带开发服务器命令；本项优先提升内部部署的稳定性，同时保留「无法推断时仍可导入」的便利性。

### 6.1 需求

- 用户显式声明的启动命令（manifest/entry.start 或已识别的项目启动约定）优先，LWA 不用自动模板覆盖。
- 没有显式命令时，Flask/Django 若能唯一推断 WSGI 入口，由生成模板在镜像内补齐 Gunicorn 并以其启动；不要求用户项目事先把 Gunicorn 写入 requirements/pyproject。
- LWA 不修改用户源码中的依赖文件；平台补齐的生产服务器属于生成 Dockerfile 的运行时依赖，并在 manifest/生成记录中可追溯。
- WSGI 入口无法唯一证明时保留 `flask run` / `manage.py runserver` fallback，不阻断导入，但在 manifest、管理页与 doctor 显著警告。
- 本项仅处理 WSGI 默认模板；项目已显式使用 Uvicorn/Hypercorn 等 ASGI 服务器时保留原命令，不自动改写为 Gunicorn。

### 6.2 关键决策（已拍板）

| 编号 | 决策点 | 倾向 |
| --- | --- | --- |
| **066.a** | 命令优先级 | 用户显式命令 > 已声明生产服务器 > LWA 可证明的 WSGI 生成命令 > 开发服务器 fallback |
| **066.b** | 生产依赖归属 | 当 LWA 生成 WSGI 命令时，在 Dockerfile 内单独安装平台选定的 Gunicorn 版本范围；不回写用户 requirements/pyproject |
| **066.c** | Flask 入口推断 | 优先复用现有 `app.py` / 包布局摘要，只接受唯一可证明的 `module:app` 或应用工厂入口；多候选不猜 |
| **066.d** | Django 入口推断 | 以 `manage.py` 所在根与唯一 `*/wsgi.py` 生成 `<project>.wsgi:application`；多个 wsgi.py 时 fallback 并警告 |
| **066.e** | 低配参数 | 默认单 worker、小线程数，绑定 `0.0.0.0:<internalPort>`；不根据宿主 CPU 盲目放大 worker |
| **066.f** | fallback 警告 | manifest 诊断字段 + 管理页 + doctor 同源展示；警告不阻断内部快速部署 |
| **066.g** | 存量实例 | 仅在 `rebuild`/源码更新后重生成时应用新规则；不在升级时静默改写已运行容器 |

### 6.3 现状触点

- `scanner.py::_python_start_command()` 对 Flask/Django 固定返回开发服务器；当 `flask+gunicorn` 同时匹配时，现有框架优先级仍选 Flask。
- `scanner.py` 已有 FastAPI/ASGI 模块推断先例，可复用「只对可证明的目标自动生成」的模式。
- `dockerfile_templates.py` 会把 scanner 的 `entry.start` 转为容器 `CMD`，需同时处理 Gunicorn 运行时依赖，不能只换命令。
- `models.py`/扫描结果诊断、管理页 helpers 与 doctor 尚无「开发服务器 fallback」的同源警告。

| **066.02** | 实现 WSGI 入口推断 | 修改 `scanner.py` 及文件摘要；Flask/Django 候选必须唯一才生成 Gunicorn 目标 |

## 7. IMP-067 — 收敛 nginx 网关入口为兼容读取

> **状态**：方案 B 已拍板，规划完成（PLN-047），待实施时另开 DEV。来源：安全评审复核第 13 条。继续维持 Caddy/builtin 两种已实现后端；nginx 仅作为存量无效配置的升级兼容输入，不再是产品可选能力。

### 7.1 需求

- 所有新写入通道（CLI/init/setup、配置生成器、管理 API、示例模板）仅接受 `caddy | builtin`；输入 nginx 时明确报错并给出迁移指引。

## 8. IMP-068 — Ubuntu 22.04 的 Python 3.13 可执行安装路径

> **状态**：方案 B 已拍板，规划完成（PLN-048），待实施时另开 DEV。来源：安全评审复核第 14 条。Python 3.13 版本基线（OPS-001/IMP-036）保持不变；本项只补齐 Ubuntu 22.04 在首次安装 LWA **之前**的可执行 bootstrap 路径。

### 8.1 需求

- 为 Ubuntu 22.04 x86_64/arm64 提供一条不替换 `/usr/bin/python3` 的主推路径：官方 uv standalone → uv-managed Python 3.13 → 带 pip 的专用 venv → editable 安装 LWA。
- bootstrap 必须出现在 README/安装文档的 `pip install -e .` 和首次 `lwa setup` **之前**；不把唯一指引放在尚无法用 Python 3.10 安装/启动的 LWA CLI 里。
- 标准命令链使用 `uv python install 3.13`、`uv venv --python 3.13 --seed .venv`、`.venv/bin/python -m pip install -e .`、`.venv/bin/lwa setup`；`--seed` 是与 issue #27 升级恢复链兼容的硬要求。
- `lwa setup`/doctor 中的指引作为已能运行 CLI 后的二次诊断；应按 distro/version 输出具体建议，不再给 Ubuntu 22.04 显示不存在的 `apt install python3.13`。
- pyenv 作为需要源码编译的备选；PPA 仅作明确标注信任与架构限制的第三方选项，不作默认官方路径。

### 8.2 关键决策（已拍板）

| 编号 | 决策点 | 倾向 |
| --- | --- | --- |
| **068.a** | 主推路径 | uv standalone + uv-managed CPython 3.13 + 项目专用 `.venv`；不改系统 Python 链接与 apt 依赖 |
| **068.b** | uv 安装信任 | 只引用 Astral 官方 installer/发布物；文档同时提供「先下载审阅再执行」路径，不依赖未验证的第三方镜像脚本 |
| **068.c** | venv 与 pip | 必须 `uv venv --seed`，并以 `.venv/bin/python -m pip` 验证；不以 `uv pip` 可用代替「venv 内存在 pip 模块」 |
| **068.d** | CLI/服务解释器 | 文档、autostart 与 update 统一使用该 venv 的绝对入口；不假设 shell 已刷新 PATH |
| **068.e** | 自动化范围 | 本项不内置自动替换系统 Python；`setup --script` 输出可审阅的参考步骤，真正执行仍需用户确认 |
| **068.f** | 备选与网络 | pyenv 说明编译依赖/时间成本；PPA 标记第三方信任边界；代理、系统证书与下载缓存按 uv 官方能力给出排障，不编造镜像地址 |

### 8.3 现状触点

- Ubuntu 22.04 官方 `python3` 为 3.10，但 `setup.py::_python_install_hint()` 仅接收粗粒度 `linux`，输出「apt/dnf 安装 python3.13」的泛化建议。
- `_SCRIPT_LINUX` 直接示例 `sudo apt install python3.13 python3.13-venv python3-pip`，在干净 Ubuntu 22.04 不可执行。
- LWA 包要求 Python 3.13+；因此「先运行 `lwa setup` 再看 Python 建议」无法作为 22.04 首次安装的唯一入口。
- issue #27 的 `lwa update` 使用当前解释器的 `-m pip`；uv 创建 venv 时若不 seed pip，初装虽可能借 `uv pip` 完成，后续 update 仍会断链。

| **068.02** | 实现 distro-aware 建议 | 让 `setup.py` 的 Python hint 消费 platform report 中的 distro/version；保留其他已支持系统的正确包管理建议 |

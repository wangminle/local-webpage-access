# Issue #158 的 LAN 地址选择与访问自检修复方案

> 供 LWA 维护者实施和验收。记录日期为 2026-11-09，对照基线为 `5408db1`（V0.10.0），本方案同时记录 V0.10.1-Build6574 验收候选的实现与缺口。

**目标**　即使透明代理接管公网路由，LWA 仍能选出可作为 LAN 入口的本机地址。选不出可信地址时，保留已有配置和服务，并明确说明访问入口的状态。

**架构**　系统接口信息负责判定地址来源，LAN 策略负责排序，URL 生成、写盘和自检共享选择结果。局域网与 Tailnet 的外部可达性分别由对应客户端验证。

**实现基础**　Python 标准库、各平台只读网络命令、现有 Typer CLI 和 pytest。

## 1. 根因与证据

- 在 `5408db1`，公网 UDP 探针通过 `getsockname()` 获取内核为探测目标选择的源地址。mihomo 的策略路由使三个探测目标都命中 TUN，`198.18.0.1` 随后被用于合成和写入 `lanUrl`、`routeUrl`。旧算法在 V0.0.8 的 `fb3c8d9` 已存在。V0.3.0 迁移了模块路径，V0.10.0 的升级刷新触发了这次落盘。 [Issue #158](https://github.com/wangminle/local-webpage-access/issues/158) · [旧版探测代码](https://github.com/wangminle/local-webpage-access/blob/5408db1/src/local_webpage_access/ports.py#L72-L89)
- `doctor` 用同一个探测结果比较落盘地址，因此错误地址相等时会报 OK。隔离 Linux 复现中，对错误地址发出的本机 HTTP 请求确实返回 200，`access review` 也报 OK。同期 `status` 负责展示链接。独立 LAN 客户端是否可达，仍需从客户端验证。
- 10 月 30 日记录的是特定 Windows 客户端与 Dell 之间的 Tailnet 数据通道异常，次日重启 Windows Tailscale 服务后恢复。该记录可供选择验收客户端时参考。 [既有运维记录](../4-issues/2026-10-30-Dell与Windows之间Tailscale隧道不通.md)
- `lwa update` 在 daemon reconcile 持实例锁时可能跳过刷新，外层仍显示 `ok`。此问题已登记为 `BUG-1030`，可以单独修改和验收。 [任务台账](../../task-list.md)

## 2. 从多轮建议中吸收的做法

| 建议 | 处理决定 |
| --- | --- |
| 枚举本机地址，按接口状态、类型与地址语义过滤 | 采用。优先用系统报告的 flags 和接口类型，接口名只用于识别有明确产品或系统含义的常见接口。已确认是 TUN、点对点、WireGuard 或本机 Tailscale 的地址不进入自动 LAN 候选。 |
| 排除基准测试、回环、链路本地、组播、未指定与广播地址 | 采用显式地址校验。`198.18.0.0/15` 属于基准测试网段。显式 RFC 1918 匹配会排除它，Python 的 `is_private` 会接受它。使用 RFC 1918 地址的隧道仍需要接口证据才能识别。 |
| 把 RFC 1918 作为唯一准入条件，或全局屏蔽 `100.64.0.0/10`、`veth*` 等 | 采用精确分类。已确认归属有效 LAN 接口的 IPv4 可以参与选择，包括合理配置的网桥、VLAN 和容器接口。对 Tailscale 按接口或本机实际地址识别，`100.64.0.0/10` 是共享地址空间，仅凭网段无法判定某个地址来自 Tailscale。 |
| 按默认路由 metric 选址，或绑定指定网卡重新探测公网 | 按已确认的产品规则排序。可用有线优先，其次是 Wi-Fi，再考虑符合条件的其他接口。同类按接口顺序。Linux 和 macOS 按接口名自然排序，Windows 按接口索引，同一接口内沿用系统返回的合格 IPv4 顺序。例如 `eth0=192.168.1.50` 优于 `eth1=192.168.1.10`。默认路由可用于解释现场现象。 |
| 给刷新、doctor 和 access review 提供明确原因，处理已经落盘的坏地址 | 采用。统一说明「没有候选」「来源未验证」和「已知坏地址」，并同时核对 `lanUrl`、`routeUrl`。从本机探活与独立设备观测分别呈现。 |
| 增加接口 allow/deny 配置、指定接口名或新增依赖 | 本轮沿用已有 `manualLanIp` 和 `lwa access lan show/set/auto`。若后续有 DHCP 动态地址下固定接口的具体需求，再单独设计接口选择配置。 |

地址分类参考 [IANA IPv4 特殊用途地址登记](https://www.iana.org/assignments/iana-ipv4-special-registry/) · [RFC 1918](https://datatracker.ietf.org/doc/html/rfc1918#section-3) · [Python 3.13 ipaddress](https://docs.python.org/3.13/library/ipaddress.html#ipaddress.IPv4Address.is_private)。

## 4. 实施顺序

本节是完整验收目标。候选版的已实现项和复验缺口见上表。

### P0-A 验证自动地址来源并约束写盘

1. 在 [test_lan_policy.py](../../tests/scripts/test_lan_policy.py) 加失败用例。枚举不可用时，裸 UDP 源地址 `172.19.0.1` 和未识别归属的 `100.64.0.0/10` 地址均不能生成自动 LAN URL。再覆盖可用有线、无有线时回退 Wi-Fi、只有隧道、合法网桥/VLAN/容器接口、枚举成功但无候选及显式 `manual`。
2. 在现有 `lan_network.py` 和 `ports.py` 补充小型解析结果，至少表达选中地址、接口、来源和原因。保留 `detect_lan_ip()` / `resolve_lan_ip()` 的 `str | None` 接口。系统枚举不可用时，UDP 结果只作线索。只有备用的只读信息能够确认地址属于合格接口时，才可发布该地址。没有确认时返回无自动地址，并提示 `lwa access lan show` 和手工设置。对无法枚举接口的旧环境，这一行为从「直接发布 UDP 源地址」收紧为「保留旧记录并提示」。
3. 保留现有 [refresh_network_entries](../../src/local_webpage_access/access.py) 的空地址护栏，同时让 CLI、管理页和 daemon 复用解析原因。无法确认来源时，批量刷新保留 manifest 和运行中的 Caddy 配置。启动或重建时继续生成回环健康检查入口。已有实例可沿用合法旧 URL 并标为待复核，新实例的 LAN URL 留空。已知坏链接可保留供排查，但展示层隐藏或标为不可用，重算 Caddy 配置时不得用它生成站点主机名或证书 SAN。
4. 复用短 TTL 候选缓存，在单次批量操作内保持一致选择。避免把暂时无候选永久缓存。显式手工策略仍具有优先级，WSL 的 guest、Windows 宿主与 LAN 暴露判断继续走现有分层逻辑。

### P0-B 统一已落盘链接的判断

1. 在 [test_doctor.py](../../tests/scripts/test_doctor.py) 加失败用例。当前 LAN 和 `lanUrl` 正常、仅 `routeUrl` 为 benchmark 时应 WARN。补充两种地址均异常、无候选且有旧链接、以及两者与有效当前入口一致的对照。
2. 让 `doctor` 与 `access review` 同时核查两个落盘 URL，复用对已知不适合发布的地址或接口的判断。仍受支持的回环入口与 WSL 路径继续按各自语义判定。已知坏地址给出明确 WARN；来源未知时用「无法确认」描述，并保持本机服务健康与外部可达性的区分。存在可信替代地址时提示刷新，否则优先提示查看候选和设置手工地址。
3. 沿用 `status` 对已知坏链接的隐藏或标记。自动选出可信地址后，以现有刷新流程修复两个 URL，并同步在线 Caddy 的 LAN 主机及证书覆盖。Tailscale 探测暂时未知时，应保留可确认的 Tailnet 入口，避免恢复已知坏的旧 LAN 主机名。检查已有 JSON 字段是否足以表达结果，有消费端需要时再补充精简的原因字段。

### P0-C 回归、实机与发布验收

1. 先运行定向回归，再运行全量门禁。验收要求为现有测试和新加的地址、状态及 TLS 回归全部通过。

   ```bash
   .venv/bin/python -m pytest -q \
     tests/scripts/test_lan_policy.py tests/scripts/test_doctor.py \
     tests/scripts/test_access.py tests/scripts/test_access_workflow.py \
     tests/scripts/test_status_lan_freshness.py tests/scripts/test_manager_api.py \
     tests/scripts/test_wsl_network.py tests/scripts/test_bug1025_tailscale_tls.py
   bash tests/gate.sh
   ```

2. 在 Dell Ubuntu 24.04 使用独立测试工作区或经安排的维护窗口。开启 mihomo auto-route，用 `ip -4 route get 8.8.8.8` 记录公网探测路径，用 `lwa access lan show` 核对 LAN 选址。报告中的接口同时可用时，预期有线 `enp0s31f6` 的 `192.168.1.14` 优先；受控断开后确认是否切换到仍在线的 Wi-Fi。分别记录 TUN 开关两种状态。
3. 检查 `lwa access refresh`、manifest、管理页、`lwa doctor` 和 `lwa access review`。有旧坏链接时先确认诊断能发现，刷新成功后核对两个 URL 都切到正确地址。服务健康且链接一致时允许本机检查恢复 OK。分别验证 `lwa access lan set 192.168.1.14`、后台读到新策略，以及 `lwa access lan auto` 恢复默认选择。实例被锁而跳过时单独记录，关联 `BUG-1030`。
4. 从独立 LAN 客户端请求当前发布的别名和端口入口，从独立 Tailnet 节点请求 Tailnet 入口。按实际启用的 HTTP/HTTPS 模式检查响应、内容及证书，覆盖 TUN 开关和地址切换。记录测试源设备、目标地址、协议、状态码和结果，登记到 `CHK-536`。
5. 在 [运维手册](../../docs/operations-playbook.md) 和 [访问复核 Skill](../../src/local_webpage_access/skills/lwa-review-access-urls/SKILL.md) 更新实际落地的降级和诊断口径。待补项与验收结果明确后，再按项目发布流程处理 #158 和版本号。

## 5. 临时恢复与关联项

原生 Ubuntu 上，若 `192.168.1.14` 仍是本机可用的有线 LAN 地址，V0.10.0 可先在工作区 `local-web.yml` 设置 `lanIpStrategy: manual` 与 `manualLanIp: 192.168.1.14`，然后运行 `lwa access refresh`。包含新 CLI 的版本可用 `lwa access lan set 192.168.1.14` 完成同一设置，再用 `lwa access lan auto` 恢复默认选择。

`BUG-1030` 的交付条件是区分锁竞争与其他跳过原因，只重试锁竞争的实例并设置总等待上限，仍有实例占用时报告部分完成并列出实例。等待 daemon 心跳就绪和等待 reconcile 释放实例锁分别验证。 [升级流程](../../src/local_webpage_access/updater.py)

# LWA 真实应用跨系统 Eval 方案与执行计划

> 面向维护者与执行 Agent 的内部方案。日期：2026-10-12。编制时状态：方案已编制，评测尚未执行。后续实测范围见 [类型化结论报告](../2-achievement/2026-10-19-真实应用跨系统Eval类型化结论.md)。
> 后续逐项执行时使用 executing-plans 技能；本文件不表示机器已接通、候选应用已适配或测试已通过。

**目标：** 通过真实 GitHub 应用在 macOS、Ubuntu 24.04、Debian WSL2 上的部署、更新、换源与恢复，建立可复现的 LWA 能力证据，并把缺陷转为回归测试。

**组织方式：** 固定一份 LWA 版本与应用版本清单，各宿主运行相同的分层用例；分别记录直接部署、配置后部署、人工修补和能力边界。先完成小规模试跑，再扩展矩阵，故障注入与宿主重启单独安排。

**工具：** LWA CLI、Git、Docker/Compose、Caddy、systemd/launchd、浏览器功能验证、HTTP 探针，以及后续按需补齐的 Python 证据采集脚本。本文不引入新的产品功能，也不要求先建设大型评测平台。

## 1. 需要回答的问题

1. 用户拿到一个未经 LWA 团队改造的真实项目，能否正确识别并部署？
2. 页面、资源、后端和持久化是否实际工作，而不只是进程存活或首页返回 200？
3. 更新后是否真的运行新版本，原来的数据、端口、别名、配置是否保留？
4. 更换源码来源或依赖下载源时，身份、版本、实际构建内容是否一致？
5. 网络、构建、启动或健康验证失败时，LWA 是否如实报告，是否破坏原有服务？
6. 同一项目在不同宿主上的差异来自 LWA、项目本身、架构还是网络环境？
7. 对超出能力的应用，能否明确说明限制、给出可行动的诊断？

第一轮定位为能力基线。它可以发现缺陷，也可以证明某些范围尚未支持；不预设所有候选应用都必须部署成功。

## 3. 环境矩阵

### 3.1 已知环境与待核实信息

| 环境编号 | 宿主 | 当前信息 | 正式执行前补齐 | 可支持的结论 |
| --- | --- | --- | --- | --- |
| H-MAC | 当前 Mac | 本会话在 Mac 工作区中进行 | macOS 版本、架构、内存、磁盘、Docker 后端及版本、现有服务 | 该 macOS 与运行时组合的实测结果 |
| H-UBU | Ubuntu 测试环境 | 用户确认 Ubuntu 24.04 | 接入条件（另存本地）、架构、资源、Docker、systemd、网络、是否承载现有服务 | 该 Ubuntu 24.04 主机的实测结果 |
| H-DEB-WSL | 待提供的 Windows/WSL 主机 | 用户考虑准备，尚未提供 | Windows/WSL 版本、Debian 版本、网络模式、Docker 后端、systemd、远程接入 | Debian 用户空间在指定 WSL2 组合下的实测结果 |
| H-DEB-NATIVE | 后续可选 VM/实机 | 未提供 | 完整 Debian 系统、独立内核与启动环境 | 补齐原生 Debian 安装、自启、重启与网络证据 |

Debian WSL 首选 LWA 当前支持矩阵内的 Debian 13；如实际准备的是 Debian 12，准确记录即可。不得把表中建议当作已经安装的事实。架构均以实际采集为准，不根据主机名称推断。

Ubuntu 的一个版本、Mac 的一个版本、WSL 的一个版本，均不能代表整个系统家族。若 Mac 为 arm64 而 Ubuntu 为 amd64，观察到的差异同时包含系统与架构因素，需同架构复现后才能归因。

### 3.2 Debian WSL 的专门要求

- 使用 WSL2。按 LWA 当前代码，WSL 包版本下限为 2.1.5，且 systemd 必须为 PID 1；这些是 LWA 门禁，不是微软启用 systemd 的最低版本声明。
- 工作区与源码副本放在发行版 Linux 文件系统中。`/mnt/c` 等 Windows 挂载位置单独作为路径限制负例。
- 首轮建议使用发行版内 Docker Engine，以便比较 Ubuntu；若机器已采用 Docker Desktop integration，记录该组合并单独计分。不要同时启用两个后端后把冲突算成普通部署结果。
- 固定 NAT 或 mirrored 网络模式。分别验证 WSL 内部、Windows 宿主、另一台 LAN 设备三条访问路径；Windows localhost 成功不能替代 LAN 成功。[微软 WSL 网络说明](https://learn.microsoft.com/en-us/windows/wsl/networking)
- 分开执行“服务重启”“目标发行版终止后重新启动”“Windows 重启后重新启动发行版”。自动唤起发行版属于 Windows 侧额外条件，必须记录。
- systemd 服务本身不会保持 WSL 实例一直存活，因此 WSL 自启通过不能外推为裸机常驻可靠性。[微软 WSL systemd 说明](https://learn.microsoft.com/en-us/windows/wsl/systemd)

报告标题必须写“Debian 版本 + WSL2 + Docker 后端”，不得简称“Debian 裸机通过”。原生 Debian 暂记未测，不阻塞前两个宿主的试跑。

### 3.3 隔离与资源预算

1. 每台宿主使用独立评测目录、Python 环境、实例标识、端口与证据目录。先盘点现有 manager/gateway/daemon/autostart、Docker context、容器和挂载。
2. 独立目录不等于完整隔离：固定监听端口、服务单元名称、Docker daemon 配置仍可能共享。若无法证明无冲突，使用独立 VM 或独立测试机，不直接安装第二套自启单元。
3. 共享宿主可先做不影响现有服务的应用测试；Docker daemon 换源、系统代理、防火墙、重启、磁盘耗尽等宿主级动作放到隔离环境或明确的维护窗口。
4. 建议起步资源为 4 vCPU、8 GiB 可用内存、40 GiB 空闲磁盘；这是执行预算，不是新增产品最低要求。实际资源更低时记录真实数值，并串行构建。
5. 每宿主构建并发固定为 1；不同宿主可由执行器并行。资源压力场景最多保留约定的少量活动实例，禁止无限堆积。
6. 禁止对共享 Docker 执行全局 prune；清理只按本轮已登记的实例、镜像、卷和网络清单进行。

## 4. GitHub 样本发现与冻结

### 4.1 筛选流程

先建立 20～30 个候选的发现清单，再按类别冻结约 11 个首轮样本。搜索以技术形态为主，例如静态网页、Vite 应用、Node SQLite、Python 自托管、monorepo、SSR、外部数据库；Stars 只作参考，不作入选门槛。

逐个检查 README、许可证、依赖清单、锁文件、目录树、启动入口、Dockerfile/Compose、升级说明。优先选择能在局域网独立运行、有可验证业务动作、资源适合小主机的项目；需要付费服务或生产密钥的项目不进入首轮主集。公开仓库并不自动等于可再分发，源码归档遵循其许可证并保留声明。

每个候选提前写清：入选理由、期望能力层级、主要功能断言、外部依赖、是否有真实升级路径、最大执行预算。一个项目失败后不能悄悄替换；排除、替换、版本改选都保留原因和旧结果。

### 4.3 版本冻结与应用配方

正式运行前为每个样本准备一份配方，至少包含：

```yaml
sample_id: A06
repository: https://github.com/sissbruecker/linkding
group: core
source_subdir: null
versions:
  old: {ref: null, commit: null, archive_sha256: null}
  new: {ref: null, commit: null, archive_sha256: null}
expected_support: pending_review
upstream_install_doc: null
upstream_upgrade_doc: null
required_configuration: []
business_assertions: []
data_locations: []
package_manager: null
lockfile_sha256: null
image_digests: []
case_ids: []
```

上面是待填模板，含 null 的版本或关键断言不得进入正式执行。每个应用优先选择相邻、上游允许升级的稳定版本；没有 release 的项目选择两个固定提交。固定源码、依赖锁与镜像摘要；无锁文件的项目保存解析后的依赖清单并标记依赖漂移风险。

LWA Git 导入的 `--ref` 按现有帮助使用分支/标签，不假定接受提交 SHA。先把 ref 解析到 OID，导入后核对记录的 OID；若期间 ref 改变，本次作废重做。严格冻结的本地目录/ZIP 用精确提交归档并校验 SHA-256。不能把默认分支的“今天最新”当成可复现版本。

没有可行真实升级对的样本，其真实升级用例记 N/A 并注明原因；另用标记为“受控源码变更”的副本测试内容替换，后者不得计作真实上游版本升级。需推送 fork 才能制造远端变化时，在执行阶段另行明确仓库与授权；本方案不创建或推送仓库。

## 5. 测试分层与覆盖矩阵

### 5.1 两条测试路线

**产品路线：** 使用 LWA 官方 CLI、管理页或现有本机 Agent 接口导入与管理。首轮以 CLI 保证可复现，再选静态、SPA、有状态后端各一个复核管理页；现有 Agent 只按 M1 本机能力测试，不假定远程 Agent M2 已上线。

**上游对照路线：** 当 LWA 失败时，在隔离环境按相同版本的上游安装说明验证项目是否可运行。若上游使用预构建镜像，它只能证明镜像可运行；源码构建失败还需要源码构建对照，不能据镜像成功直接断言 LWA 构建有 bug。对照不计入 LWA 成功率。

执行必须先保存未经额外调整的第一次结果，再做配置或修补。修改应用源码、LWA 源码、生成的 Dockerfile/Compose、手工启动容器，都构成新的尝试，不能覆盖原结果。

### 5.2 首轮规模

| 层级 | 范围 | 计划数量或口径 |
| --- | --- | --- |
| 环境门禁 | 每个已提供宿主 | 3 个计划环境；缺席环境记 BLOCKED_ENV |
| 基础适配 | A01～A11 × H-MAC/H-UBU/H-DEB-WSL | 33 个计划单元；WSL 未到位时先跑 22 个，11 个保留未执行 |
| 完整生命周期 | A01～A06 × 三环境 | 18 组；每组按适用性展开部署、更新、换源、重启、清理 |
| 深入探索 | A07～A09 | 一台宿主先探路，能部署后同步补齐其他宿主；失败仍保留在基础矩阵 |
| 能力边界 | A10～A11 × 三环境 | 判断准确性单独计分；拒绝成功不计为部署成功 |
| 源与故障专项 | 每种机制选一个代表项目 × 三环境 | pip、apt、npm、源码来源、失败更新等逐项登记，不做全量笛卡尔积 |
| LWA 自身升级 | 三环境各一组代表实例集合 | 与应用升级分开统计 |

每条用例具有固定 ID，格式为“环境 / 样本 / 场景 / 尝试编号”。首轮冻结后，必须有逐格状态表；只有规划总数而没有逐格记录，不能宣布矩阵完成。

## 6. 单个应用的标准执行过程

### 6.1 PRE：前置准备

1. 冻结 LWA commit、应用 old/new commit、配方版本、宿主指纹和用例列表。
2. 采集系统版本、架构、Python、Node、Docker client/server、Compose、Caddy、Docker context 与镜像架构。记录代理是否启用，但不输出凭据。
3. 拍下现有实例、监听端口、服务单元、容器和卷的基线；核对评测工作区绝对路径与独立 CLI 路径。
4. 执行工作区诊断。缺少环境依赖记录为前置条件，不把它直接伪装成应用不兼容。
5. 初始化测试数据种子和功能断言；确定失败后的证据保留、数据备份与清理路径。

`lwa init` 或 Full setup 可能启动服务/安装宿主依赖，执行前完成隔离检查。已有工具环境上的应用部署通过，不等于从干净系统安装 LWA 通过；干净安装需独立 VM/系统快照另测。

### 6.2 DEP：导入与首次部署

1. 核心样本使用固定 Git ref 做首次导入；没有合适 ref 的样本以固定目录/ZIP 导入并记录缺口。
2. 保存识别 kind、sourceSubdir、运行方式、依赖/启动命令、风险提示、生成配置和 source hash。
3. 按正常用户流程启动，不手工修生成物。记录导入、安装依赖、构建、启动、就绪分别耗时与退出码。
4. 验证直接访问入口的 HTTP 状态、内容标识、关键资源和至少一个业务动作；后端补 API 写入/读取。
5. 对有前端路由的项目验证深链接刷新；对实时连接项目验证连接后的业务消息，不仅验证 HTTP 握手。
6. 对申明可使用别名的应用验证别名入口、资源、API、Cookie 路径与跳转；明确不兼容时验证拒绝理由。拒绝合理可算边界判断正确，但该入口仍不算可用。
7. HTTPS 场景使用受信任测试 CA；禁止用跳过证书验证作为通过条件。保存证书验证结果，不把私钥放进证据仓库。
8. 在另一台 LAN 设备执行同样的最小业务动作；报告分别列本机、LAN、HTTPS 结果。

### 6.3 DAT：持久化与业务证据

写入带 run_id 的文章/书签/监控项/笔记，保存业务对象 ID、内容和导出摘要。对附件保存校验和；数据库优先用应用导出或一致性备份，不直接复制正在写入的 SQLite 主文件而漏掉 WAL。

保存实例 ID、端口、别名、sourceType、source ref/OID、desiredState、配置摘要与 data 位置。更新后比较业务内容，不要求迁移后的数据库二进制 hash 相同。浏览器 localStorage 与服务器数据分开记录，A01/A07 不能充当后端持久化通过证据。

### 6.4 UPD：应用更新

| 用例 | 操作 | 必须检查 |
| --- | --- | --- |
| UPD-01 | old → new 正常升级 | 实际版本/资源/API 已变化；数据、ID、端口、别名、约定配置保留 |
| UPD-02 | 相同 OID/内容重复更新 | 如实提示无变化；没有重复实例或意外重启/数据重置 |
| UPD-03 | 目录/git 源变化后 rebuild 与 rebuild --sync | 本地副本和来源差异被正确提示，sync 后实际新内容上线 |
| UPD-04 | 新版本构建失败 | 记录命令结果与旧实例真实可用性；不得只看 FAILED/RUNNING 字符串 |
| UPD-05 | 新版本能启动但业务探针失败 | 不得误报完全成功；旧版本是否存活、是否能恢复有证据 |
| UPD-06 | 原服务停止意图后更新/恢复 | 不应悄悄把显式停用变成运行；根据冻结版本契约核对 |

成功更新每秒从外部发起一次轻量业务探针，记录中断区间、连续失败次数、首个新版本响应和稳定就绪时间。客户端重试不能抹掉服务端中断。首轮报告实际中断，不虚构“零停机”承诺。

涉及数据库迁移时先验证备份可恢复。镜像回退不等于数据库回退：恢复演练在副本上同时恢复匹配的应用和数据，记录人工步骤。冻结版本没有 rollback 命令时，不编造命令或计作原生回滚通过。

### 6.5 SRC：应用源码换源

这里的“换源”指同一个实例改变源码来源，不包括依赖镜像站。

| 用例 | 路径 | 断言 |
| --- | --- | --- |
| SRC-01 | ZIP → 目录 | 同一实例原地切换；源码、sourceType 与来源路径一致 |
| SRC-02 | ZIP → GitHub | 保留 ID/端口/数据/别名，记录目标 ref/OID |
| SRC-03 | 目录 → GitHub | 后续更新跟随新 Git 来源，不再读取旧目录 |
| SRC-04 | GitHub → 目录 | 按冻结版本能力核实反向切换；不支持时说明限制 |
| SRC-05 | 目录 A → 目录 B | 使用现有 --allow-source-change；相对路径解析为正确绝对路径 |
| SRC-06 | 相同内容、不同来源 | 即便内容 hash 不变，也正确更新来源身份 |
| SRC-07 | 无效来源/ref/子目录 | 操作失败可解释，原来源与可用内容不被半切换 |
| SRC-08 | 切源后立即再更新 | 证明没有继续从旧来源获取内容；检查持久化与配置 |

Git 仓库 A → B、Git/目录 → ZIP 作为补充边界用例，先核对契约，不默认为已支持。换源验证使用同一应用的等价副本或明确兼容版本；不能把互不相关应用强塞入同一数据库再归咎于 LWA。

### 6.6 MIR：依赖与镜像下载换源

| 通道 | 配置/机制依据 | 试验 |
| --- | --- | --- |
| pip | buildMirrors.pip、pipFallbacks、pipRetries、pipTimeout | 官方与国内源；主源失败后备用成功；全失败；禁用 fallback |
| apt（容器构建） | aptMirror、aptFallbacks、aptRetries、aptTimeout | 相同 systemDeps 下切换、404/超时、备用源成功及全失败 |
| npm | buildMirrors.npm | 官方与镜像源、锁文件 resolved 地址、失败文案；不假设存在 npm 自动 fallback 链 |
| Node 分发文件 | nodeDistBase | 仅在确实下载该文件的路径验证；未触发则 N/A |
| Docker 基础镜像 | 实际 Docker daemon/registry 路径 | 拉取失败与恢复、架构匹配；这是宿主通道，不能用 pip 成功代替 |
| GitHub 源码 | 导入使用的 git 网络路径 | DNS/代理/超时、错误 ref；原实例与来源元数据保持一致 |

至少设置三类配置：官方源、国内源、可控故障源。主源失败由本轮隔离网络中的 HTTP 服务/代理注入拒绝连接、超时、404/503；不攻击公共服务、不修改共享宿主全局网络。故障源必须从实际构建容器内可达，不能随手填宿主 localhost。

必须证明实际访问过目标源：保存构建日志、故障代理请求计数与最终依赖版本。缓存命中不能证明换源有效。冷构建使用独立 builder/cache 或可确认失效的测试层；没有安全冷构建入口则记录证据缺口，不对共享环境全局清缓存。

源切换可能改变包版本，优先保持锁文件与包 hash 相同；无法保持时明确标注，避免把版本变动误当网络效果。测试构建容器内 apt 不等同替换 Ubuntu 宿主 apt 源。

### 6.7 REC：服务恢复与宿主差异

代表集：A01 静态、A02 SPA、A05/A06 有状态后端。每个宿主覆盖以下适用场景：

- 正常 stop/start/restart；显式停用后不被 reconcile 意外拉起。
- 单个评测容器异常退出，观察恢复、退出码、实际服务和状态一致性。
- manager/daemon/gateway 受监管重启，检查无重复进程、无端口漂移。
- Docker 晚于 LWA 就绪，记录能力探测、自愈时间与失败提示。
- Ubuntu 宿主重启；Mac 注销/登录与重启分别记录，注明 launchd 登录条件。
- WSL 目标发行版终止并重启，及 Windows 重启后的启动流程；不以重启容器代替。
- LAN 地址变化后刷新访问地址与 HTTPS 入口；只能在隔离网络或维护窗口执行。

允许恢复时限先设为观测目标：运行时就绪后 180 秒内恢复，否则记录超过目标；是否属于产品缺陷按冻结版本承诺判定。无法安排宿主重启则该项明确 NOT_RUN，不用进程重启替代。

### 6.8 LWA-UP：LWA 自身升级

独立选择一个历史发布版与一个固定目标版本，在干净、完整 Git checkout 和独立 Python 环境中执行。记录 upstream、源 ref/OID、pip 状态与运行进程版本；不能使用当前带未提交改动的开发目录作为正式成功样本。

升级前运行静态、SPA、有状态后端代表实例并写入测试数据。通过冻结版本真实支持的 `lwa update` 参数选择已冻结目标；若只能跟随远端分支，就锁定并核验实际 OID，漂移时重做。检查 CLI、后台服务版本一致，registry/配置兼容、实例和业务数据仍可用、访问入口不变。

补测离线/代理失败、pip 缺失、脏工作区、分叉或浅克隆等已有拒绝路径；拒绝必须可解释，且记录源码/运行态是否变化。`lwa update --no-pull` 只能算运行时刷新，不能算跨版本升级通过。恢复时应用代码、Python 环境和工作区格式必须匹配，不能假设简单 git reset 就能撤销升级。

### 6.9 CLN：卸载与收尾

先验证不 purge 移除的约定数据保留行为，再对可丢弃副本测试显式 purge。对比 PRE 清单，检查本轮进程、容器、端口、挂载、网络与缓存残留。失败现场采证并归档后才清理；不得因清理操作抹掉最后一份可用备份。

## 7. 命令与执行约束

以下是依据当前 CLI 的命令模板，变量必须来自已冻结配方，且在隔离检查后执行；本次没有运行这些部署命令。`LWA_BIN` 是本轮独立环境的 lwa 绝对路径，`EVAL_WS` 是已完成隔离初始化的工作区。

```bash
cd "$EVAL_WS"
"$LWA_BIN" version
"$LWA_BIN" doctor --json
"$LWA_BIN" import --from-git "$APP_REPO" --ref "$APP_OLD_REF" -n "$CASE_NAME"
"$LWA_BIN" status "$INSTANCE_ID"
"$LWA_BIN" start "$INSTANCE_ID"
"$LWA_BIN" logs "$INSTANCE_ID" -c build
"$LWA_BIN" import --from-git "$APP_REPO" --ref "$APP_NEW_REF" --update "$INSTANCE_ID"
"$LWA_BIN" import --from-dir "$SOURCE_B" --update "$INSTANCE_ID" --allow-source-change --yes
"$LWA_BIN" rebuild --sync "$INSTANCE_ID"
"$LWA_BIN" access review --json
```

这些行对应不同用例，不是一段无需判断即可连跑的脚本。首次导入后先从实际输出登记 INSTANCE_ID；每条命令后执行该用例的业务断言与快照。子目录样本按配方单独加入 `--subdir`。不把 `--path-alias` 和 `--update` 拼接，别名设置使用已有独立命令。`access review` 是平台检查，不能替代应用业务断言。

当前普通 CLI 按工作目录定位工作区，执行器必须固定 cwd，不虚构通用 `--workspace` 选项。每条命令记录 argv、cwd、开始/结束时间、返回码、stdout/stderr；对可能包含密钥的参数脱敏。

单次 Git 获取初始预算 5 分钟、构建 20 分钟、启动就绪 3 分钟；复杂项目可在第一次执行前单独登记 40 分钟构建预算。这些是评测超时，不是产品 SLA。总预算耗尽保存现场、取消本轮进程组并检查残留，记超时或环境阻塞，不无限重试。

每个正式用例首次结果必须保留。疑似临时网络问题允许最多一次相同条件重试；排障尝试另编号，禁止只选成功的一次入表。对稳定性代表用例安排 3 次独立重复，同时报告首次成功与重复一致性。

## 8. 结果分类、指标与判定

### 8.1 三个独立维度

| 维度 | 枚举 | 含义 |
| --- | --- | --- |
| 执行结果 | PASS / FAIL / BLOCKED_ENV / NOT_RUN / N/A | 有证据满足断言 / 违背断言 / 前置环境未满足 / 未执行 / 有理由不适用 |
| 适配方式 | DIRECT / CONFIGURED / PATCHED / UNSUPPORTED | 标准输入即可 / 使用公开配置入口后成功 / 修改代码或绕开平台后成功 / 明确能力边界 |
| 原因归属 | LWA / APP / ENV / NETWORK / UNKNOWN | 需证据归因；暂不清楚时保持 UNKNOWN |

标准输入包括测试账号等应用必需参数。额外指定启动命令、build hook、systemDeps 等归入 CONFIGURED，并记录配置量、人工时间；即便配置合法，也不能冒充自动识别成功。预构建制品导入与源码构建分开计数。

UNSUPPORTED 可以在“边界判断”用例中 PASS，但该项目部署能力仍为未支持。超时发生于已启动的产品操作且违反其断言时记 FAIL；尚不满足执行前置条件才记 BLOCKED_ENV。不能用 ENV 标签替产品失败开脱，缺陷归属可以后续修订但需保留依据。

### 8.2 报告必须公开的分母

以冻结矩阵中同一层级的单元为统计对象，场景通过率不能与应用通过率混加：

- 有效计划数 `N = 冻结单元总数 - 有依据的 N/A`。
- 覆盖率 `C = (PASS + FAIL) / N`；BLOCKED_ENV、NOT_RUN 留在分母。
- 已执行单元通过率 `P = PASS / (PASS + FAIL)`，与覆盖率同时显示；分母为 0 时写“未测”。
- 直接部署成功率 `D = DIRECT 且部署 PASS 的项目-宿主单元数 / 有效计划部署单元数`。
- 配置后累计成功率 `S = (DIRECT + CONFIGURED) 且部署 PASS 的单元数 / 同一分母`；PATCHED 单列。
- 生命周期完成率：适用生命周期必测场景全部通过的核心项目-宿主组数 / 有效核心组数；任一阻塞或未测不得算全通过。
- 边界判断准确率、数据保留结果、假绿次数、首次成功率、人工干预次数、停机时间和冷/热构建时间分别呈现。

按宿主、核心/探索/边界、教程/成品、架构分别汇总，同时公开全量逐格结果。边界样本拒绝正确不能抬高部署率。首轮样本是有目的抽样，不能据此推算“GitHub 任意网页应用成功概率”。

### 8.3 退出标准

**基线评测完成：** 已提供宿主的计划单元全部获得明确结果和证据，失败已归档，未提供宿主单独列缺口；这不等于兼容性达标。三环境总计划只在 WSL 也完成后才能宣称完成。

**后续发布门禁建议：** 冻结且宣称支持的核心集，在指定宿主上直接或配置后可用；数据丢失、假绿、误操作其他实例、失败后不可恢复等严重问题为 0；适用更新/换源/恢复场景全部通过，代表场景 3 次重复一致。边界项目未支持可以保留，但需准确诊断和公开限制。采用发布门禁时应明确具体版本与支持集，不反向改写本轮失败记录。

暂不设置一个掩盖风险的综合分数，也不以“整体 95%”抵消一个数据丢失问题。

## 9. 证据、报告与归档

公开文档只保留方法、冻结样本和系统类型化结论；真实主机、SSH 接入与操作步骤集中在本地操作手册，逐机分析与原始证据仅留已忽略的检查点目录。详见 [样本清单的文档分层约定](../../tests/evals/evals-readme.md#文档与证据分层)。本方案保留 2026-10-12 的计划基线，实际结果见 [类型化结论报告](../2-achievement/2026-10-19-真实应用跨系统Eval类型化结论.md)。

每条结果至少保存 run_id、case_id、尝试编号、LWA commit、应用 commit、环境编号、操作起止时间、退出码、断言结果、适配方式、原因归属、人工动作和证据索引。时间使用带时区 ISO 8601；台账使用 Asia/Shanghai 的 `YYYY-MM-DD HH:MM`。

报告每个失败回答四个问题：期望是什么、实际发生什么、怎样最小复现、如何区分 LWA 与上游/环境原因。截图辅助说明 UI，不替代结构化断言。截图、日志与结果必须来自同一轮版本。

## 10. 缺陷闭环与版本对比

1. 保存第一次失败现场，归类识别、依赖、构建、启动、就绪、访问、数据、更新、切源或恢复阶段。
2. 先核对运行时和网络，再按需要做上游对照，仍不确定则保留 UNKNOWN。
3. 查根目录台账及上一阶段计划是否已有同类问题；已知问题引用原编号，新增问题才分配 BUG/CHK 等编号，避免重复立项。
4. 提取不依赖外网的最小回归用例，覆盖根因；真实应用保留为后续验收样本。
5. 修复后先跑相关回归，再对同一应用、相同环境和依赖重跑原用例；必要时补另一个宿主验证。
6. 修复前后属于不同 LWA commit，生成独立结果并给出差异表；不能在原基线中替换掉失败。
7. 更新项目台账和已验证支持范围；新增产品行为仍走项目既有设计、实现和审查流程。

评测可以与 2026-10-11 改造计划配合：先固定当前版本得到基线，S1/S2/S3 阶段分别用相同样本复测。新功能尚未交付时记能力差距；交付后把对应目标转成强制门禁。

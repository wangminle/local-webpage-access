# 第一部分：问题分析

## 1. 背景与触发案例

### 1.1 触发事件

2026-08-10，在 lwa 上部署 `home-bookshelf-management-v1`（一个 FastAPI + SQLite + Vue 全栈项目），从 `lwa import` 到最终 `lwa start` 成功，经历了 **6 轮手动排查与修正**。整个调试过程暴露的不是单个 bug，而是 scanner 架构范式的系统性缺陷。

本文以该部署的完整过程作为**实证锚点**——所有设计论断都可回溯到这个真实案例的具体表现。

### 1.2 项目结构

```
home-bookshelf-management-v1/
├── backend/
│   ├── requirements.txt          # fastapi, uvicorn, sqlalchemy, alembic, pyzbar ...
│   ├── pyproject.toml
│   ├── app/
│   │   ├── main.py               # FastAPI 应用入口
│   │   ├── config.py             # database_url 从环境变量读，默认 sqlite:///./data/bookshelf.db
│   │   └── ...
│   ├── alembic.ini               # script_location = alembic（相对路径）
│   ├── alembic/
│   │   ├── env.py                # 用 settings.database_url（从环境变量读）
│   │   └── versions/
│   ├── Dockerfile                # 项目自带（含 docker-entrypoint.sh 逻辑）
│   ├── docker-entrypoint.sh      # alembic upgrade head && uvicorn
│   └── static/                   # 前端构建产物挂载点（构建前为空）
├── frontend/
│   ├── package.json              # vue, vite
│   ├── vite.config.ts            # base = import.meta.env.BASE_URL
│   └── src/
│       └── api.ts                # BASE = ${import.meta.env.BASE_URL}api/v1
└── deploy/
    └── docker-compose.yml        # 项目自带的 compose
```

**关键特征**：
1. 代码在 `backend/` 子目录（非根），前端在 `frontend/` 子目录
2. 后端从 `backend/static/` 服务前端 SPA（构建后注入）
3. 数据库用相对路径 `sqlite:///./data/bookshelf.db`
4. alembic 迁移 `script_location=alembic` 是相对 cwd 的
5. 项目自带 Dockerfile 和 docker-compose.yml

### 1.3 调试过程的 5 层卡点链

部署过程暴露了一条**有依赖顺序的卡点链**——每一层的错误都掩盖了下一层的问题，只有修好上一层才能看到下一层的症状：

| 层 | 卡点 | 症状 | 修正方式 | 下一层暴露的卡点 |
|---|---|---|---|---|
| **L1** | scanner 只扫根目录 → 误识别为 static | `lwa import` 识别为 `static`，不生成 Dockerfile | 手改 `local-web.json`：`kind: python, runtime: docker-compose` | L2: COPY 路径 |
| **L2** | Dockerfile COPY `current/requirements.txt` → 文件在 `backend/` | build 失败或容器缺依赖 | 手改 `entry.start` 和 COPY 逻辑 | L3: CMD 解析 |
| **L3** | `_to_exec_form` 把 `docker-entrypoint.sh (alembic...)` 拆碎 | 容器报 `executable file not found in $PATH` | 改用 `sh -c '...'` 单引号包裹 | L4: alembic cwd |
| **L4** | `alembic -c backend/alembic.ini` 时 `script_location=alembic` 相对 `/app` | 容器 restart 循环：`Path doesn't exist: alembic` | 改用 `cd backend && alembic upgrade head && cd /app` | L5: DB 路径 + 镜像重建 |
| **L5** | 相对 DB 路径 + lwa 轻量 start 跳过 build + 运行容器未传导当前配置 | alembic 写 `/app/backend/data`，uvicorn 读 `/app/data`，数据库「丢表」；改了 Dockerfile 后容器仍运行旧 CMD | 绝对路径 `DATABASE_URL` + 强制重建/重建容器 | — （最终成功） |

### 1.4 「假信号」问题

这 5 层卡点中最折磨人的不是「识别错了」——那是第一层，改 manifest 就好。折磨人的是 **lwa 在每一层都给出「看似成功了」的假信号**：

```
L1: 改了 manifest → 识别"成功"了
    → 假信号：lwa 接受了 python/docker-compose 配置
    → 实际：COPY 路径仍然按根目录生成，build 才暴露

L2: 改了 entry.start → Dockerfile "生成"了
    → 假信号：日志显示「已生成 Dockerfile」
    → 实际：_to_exec_form 拆碎了 &&，CMD 参数错乱

L3: 用 sh -c 包裹 → CMD "正确"了
    → 假信号：Dockerfile 的 CMD 看起来对了
    → 实际：alembic script_location 相对 cwd 找不到，restart 循环

L4: 改成 cd backend → 命令"正确"了
    → 假信号：命令逻辑正确
    → 实际：lwa 走「轻量 start」没 rebuild，容器跑旧 CMD

L5: docker compose build → "重建"了
    → 假信号：build 命令成功执行
    → 现场现象：构建输出大量 CACHED，新 CMD 未传导到容器
    → 边界：这不足以证明「CMD 指令不参与缓存键」；还需核对 Dockerfile hash、image ID、container Config.Cmd 与 compose 重建路径
```

**根因**：lwa 的每一层都「成功执行了它该做的事」，但**不校验上游修改是否真正传导到运行时**。`lwa start` 在轻量路径下甚至不重新读 Dockerfile，所以改了 Dockerfile 它毫无反应，也不告知「我跳过了重建」。

### 1.5 一句话根因

> **scanner 缺少「布局」维度。它知道项目是什么类型（python/node/static），但不知道这个项目的源码在哪个子目录、迁移脚本相对哪个 cwd、数据库路径怎么解析——而这些「布局事实」才是部署正确性的真正决定因素。**

## 2. 当前架构剖析

### 2.1 判定流程：贪婪即时分支

`scanner.py` 的 `Scanner.detect()` 采用**贪婪即时分支**策略——遇到第一个匹配的规则就下结论，不再回头：

```python
# scanner.py:281-330（简化）
class Scanner:
    def detect(self, project_dir: Path) -> DetectionResult:
        summary = summarize(project_dir)          # ← Layer 0: 收集事实（但只看根目录）
        result = DetectionResult()

        # 1. 重型数据库优先判断
        heavy = self._detect_heavy_db(summary)
        if heavy:
            result.pending = True                 # ← 命中即 return，不再看其他可能
            return result

        # 2. SQLite 检测
        self._detect_sqlite(summary, result)

        # 3. 主类型识别（贪婪分支）
        if summary.has_package_json and self._is_real_node(summary):
            self._detect_node(summary, result)    # ← 命中即判定为 Node
        elif has_python_signal:
            self._detect_python(summary, result)  # ← 命中即判定为 Python
        elif summary.has_package_json:
            self._detect_node(summary, result)
        elif summary.has_index_html or summary.has_html:
            self._detect_static(summary, result)  # ← 兜底判定为 static
        else:
            if _has_index_anywhere(project_dir):
                self._detect_static(summary, result)
            else:
                result.pending = True             # ← 全部失败

        return result                              # ← 返回唯一的 DetectionResult
```

**关键问题**：

1. **只收集根目录事实**：`summarize()` 的 `root.iterdir()`（scanner.py:99）只遍历项目根目录的顶层文件。`_walk(root, max_depth=3)`（scanner.py:130）虽然递归子目录，但**仅用于统计 `total_files` 和 `sqlite_files`**，不参与项目类型/依赖识别。

2. **贪婪分支不可回溯**：一旦命中 `_detect_node` / `_detect_python` / `_detect_static`，就不再考虑其他可能性。对 `backend/+frontend/` 结构，根目录无工程文件 → 走到 `_has_index_anywhere` 兜底 → 命中 `frontend/index.html` → 判定 static。这个判定**没有任何机制可以质疑它**。

3. **confidence=high 无验证**：`_detect_static`（scanner.py:418-423）对纯静态场景设 `confidence="high"`，但对 `backend/+frontend/` 结构也走到同一分支并设 `confidence="high"`——即使 `backend/requirements.txt` 就在那里，scanner 根本没看过它。

### 2.2 数据流：单值贯穿，无校验环节

从识别到运行的完整数据流是一条**单值链**，每个环节都无条件接受上游的结论：

```
summarize(root)
    ↓ FileSummary（根目录事实子集）
Scanner.detect()
    ↓ DetectionResult（单值：kind + runtime + entry + ...）
build_manifest_from_detection()          # importer.py:1512
    ↓ InstanceManifest（单值：kind + runtime + container/static + entry）
importer._import_zip_locked()
    ↓ 写入 local-web.json + registry
lifecycle.start_instance()
    ↓ 读 manifest（单值）
hosting.host_container()
    ↓ generate_dockerfile(manifest)     # 无条件信任 manifest.entry
    ↓ generate_compose(manifest)        # 无条件信任 manifest.container
    ↓ docker compose build + up
    ↓ _wait_for_http(host_port)         # 唯一的「验证」——但只验证「能访问」，不验证「配置对不对」
```

**「识别成功」与「能跑起来」之间无验证关系的精确论证**：

- `DetectionResult.confidence` 表示的是**识别器对类型判断的把握**，不是**部署配置的正确性**
- `_wait_for_http`（hosting.py:609）只做 HTTP GET `/`，验证的是「容器起了且端口通」，但 SPA 首页 200 ≠ 后端 API 可用 ≠ 数据库迁移成功
- 从 `DetectionResult` 到容器启动，中间有 **5 个转换环节**（manifest 构建 → Dockerfile 渲染 → compose 渲染 → Docker build → 容器启动），**每个环节都可能引入错误，但没有任何环节做交叉验证**

### 2.3 当前架构的 5 个隐含假设

scanner 和模板体系的正确性依赖 5 个隐含假设。**每个假设对 80% 的简单项目成立**，但对全栈/子目录/复杂项目不成立：

| # | 隐含假设 | 代码位置 | 对哪些项目不成立 | home-bookshelf 的违反 |
|---|---|---|---|---|
| **H1** | 工程文件在项目根目录 | `scanner.py:99` `root.iterdir()` 只遍历顶层 | 代码在 `backend/`、`server/`、`api/` 子目录 | requirements.txt 在 `backend/`，package.json 在 `frontend/` |
| **H2** | 启动命令是单条空格分隔 | `dockerfile_templates.py:625` `_to_exec_form` 用 `shlex.split` | 命令含 `&&`、`\|\|`、`;`、`$()` 或调用 entrypoint 脚本 | `docker-entrypoint.sh alembic upgrade head && uvicorn ...` |
| **H3** | 应用用绝对路径或 runtime_paths 读数据库 | `compose.py:191` 仅 RUNTIME_ROOT 布局设 `DATABASE_URL` | 应用用相对路径 `sqlite:///./data/...`，且 alembic/uvicorn 在不同 cwd 执行 | `sqlite:///./data/bookshelf.db`（相对路径），alembic 在 `/app/backend/`，uvicorn 在 `/app/` |
| **H4** | Dockerfile 由 lwa 模板统一渲染，用户不手改 | `dockerfile_templates.py` 生成 `apps/<id>/docker/Dockerfile`，`write_text` 无条件覆盖该生成物 | 项目自带 Dockerfile，或用户手改 lwa 生成的 Dockerfile | 项目自带 `backend/Dockerfile` + `docker-entrypoint.sh` 未被采用；对 lwa 生成 Dockerfile 的手工修改会被下次完整重建覆盖 |
| **H5** | 改了 Dockerfile/manifest 后下次 start 会重建 | `lifecycle.py:268` `_is_deployed_container` 为 True 时走轻量路径，不 rebuild | 任何需要新镜像或新容器配置的修改 | 用户改了 Dockerfile CMD，但轻量 start 未重建；后续手工 build 的传导链也未留存足够证据 |

**这 5 个假设的危险之处**：单独看每个都「对大多数项目合理」。但只要项目复杂度跨过「单根目录扁平」这条线，它们会**同时**失效，而且失效方式互相纠缠——H1 导致识别错误 → H4 导致用户的自救被吞 → H2 导致 CMD 错乱 → H3 导致数据库不一致 → H5 导致修复无法传导。每一层的修复都被下一层的假设阻挡。

### 2.4 与 IMP-057 设计的关系

现有的 [导入预检与 Monorepo 识别增强](./导入预检与Monorepo识别增强-20260810.md)（IMP-057）设计计划已经开始补 scanner 的「布局」维度——通过 monorepo 包分类器识别 npm workspaces 结构。但 IMP-057 的设计**仍然基于即时判定范式**：

- IMP-057 §4.4 的选主包决策表是「0/1/≥2 个 web_server」的即时分支，不是候选列表
- IMP-057 §4.5 的 entry 约定生成的是**单个** `entry.start`/`entry.build`，不是多候选
- IMP-057 没有验证环节——选完主包后直接进 manifest，build 失败不会回溯到「另一个包可能是对的」

**本文档与 IMP-057 的关系**：IMP-057 是本文档 Layer 1（候选生成）的一个**具体规则集**。本文档定义框架，IMP-057 填充 monorepo 识别规则。两者互补，不冲突（详见 §9）。

## 3. 失败模式分类

本节将 home-bookshelf 部署中暴露的问题，以及历史 BUG-4xx 系列中的同类问题，按**识别器的知识盲区**进行系统化分类。分类维度不是 bug 编号（那是零散的），而是「scanner/模板体系的哪个认知层面缺失」。

### 3.1 A 类：未知布局盲区

**定义**：scanner 不知道（或不看）项目源码的组织结构，只假设「一切都在根目录」。

| 特征 | 现有代码哪里不设防 | 表现症状 | 实证 |
|---|---|---|---|
| 代码在 `backend/` 子目录 | `summarize()` 只遍历 `root.iterdir()`（scanner.py:99） | 误识别为 static/pending | home-bookshelf：requirements.txt 在 `backend/` → 误判 static |
| npm workspaces monorepo | `_is_real_node()` 只看根 package.json 的 deps（scanner.py:345-354） | 根 package.json 仅含 devDeps → pending | patent-disclosure（IMP-057 触发案例） |
| 前后端分仓（`backend/+frontend/`） | 无识别逻辑 | 误识别为 static（命中 frontend/index.html 兜底） | home-bookshelf |
| Electron 混合仓 | 无识别逻辑 | 把 Electron 包误当部署目标 | patent-disclosure（IMP-057 §1.3） |

**A 类的本质**：scanner 的 `FileSummary`（scanner.py:69-91）记录了文件摘要，但摘要的采集方式（`root.iterdir()`）决定了它**只能看到根目录的事实**。子目录里的工程文件对它完全不可见。

**已修复的历史案例**：
- BUG-004：子目录 `index.html` 被识别但托管根目录仍指向 current 根（修复：`host_static` 以 `index.parent` 为静态根）
- BUG-013：嵌套 index.html + 根目录同级资源会丢失 sibling（修复：同步整个 `current/` 再提升子目录内容）

这些修复都是**针对静态托管**的局部修正，没有触及 scanner 的根目录假设。Python/Node 子目录布局仍然完全不设防。

### 3.2 B 类：命令语义盲区

**定义**：`_to_exec_form`（dockerfile_templates.py:625-649）假设启动命令是简单空格分隔，不处理 shell 语义。

```python
# dockerfile_templates.py:625-649（核心问题代码）
def _to_exec_form(shell_cmd: str) -> str:
    try:
        parts = shlex.split(shell_cmd)     # ← 把 && 当普通 token 拆分
    except ValueError:
        return json.dumps(shell_cmd)
    while parts and "=" in parts[0] and not parts[0].startswith("-"):
        ...
    if parts:
        return "[" + ", ".join(json.dumps(p) for p in parts) + "]"
```

| 特征 | 表现 | 实证 |
|---|---|---|
| 命令含 `&&` | `["alembic", "upgrade", "head", "&&", "uvicorn", ...]` — `&&` 成了 alembic 的参数 | home-bookshelf L3；BUG-471 |
| 命令含 `\|\|` 或 `;` | 同上，操作符成为字面参数 | 通用风险 |
| 命令调用 entrypoint 脚本 | `["docker-entrypoint.sh", "(alembic", "upgrade", ...]` — 括号被拆 | home-bookshelf L3 |
| 命令含 `$()` 或 `` ` `` | subshell 不被解析 | 通用风险 |
| 环境变量前缀 `KEY=VAL cmd` | 被 `while parts[0]` 循环剥离（:640-646），但仅限首段、仅限 `KEY` 是 identifier | 多数场景被处理，但边界脆弱 |

**B 类的当前防御**：`scanner._python_start_command()`（scanner.py:621-630）知道这个问题，**仅对 alembic 场景**用 `sh -c` 包裹：

```python
# scanner.py:627-629
if summary is not None and summary.has_alembic_ini:
    cmd = f'sh -c "alembic upgrade head && exec {cmd}"'
```

**漏洞**：这个防御只覆盖 scanner 自动生成的命令。用户通过 skill/手改 manifest 写入的 `entry.start`，或非 alembic 场景的多命令启动，**完全没有防护**。`_to_exec_form` 本身不做任何 shell 操作符检测。

### 3.3 C 类：路径相对性盲区

**定义**：scanner 和模板体系不感知应用内部路径的相对性——它不知道应用的 DB 路径、迁移脚本路径、entrypoint 引用是相对于哪个工作目录的。

| 路径类型 | 问题 | 代码不设防处 | 实证 |
|---|---|---|---|
| SQLite 数据库路径 | 应用用 `sqlite:///./data/bookshelf.db`（相对 cwd） | `compose.py:191` 仅 RUNTIME_ROOT 布局设 `DATABASE_URL` | home-bookshelf L5 |
| alembic `script_location` | `script_location = alembic`（相对 alembic.ini 所在目录的 cwd） | Dockerfile 模板无 cwd 编排 | home-bookshelf L4 |
| COPY 源路径 | `COPY current/requirements.txt` 硬编码根路径 | `dockerfile_templates.py:463` | home-bookshelf L2 |
| entrypoint 脚本引用 | CMD 引用 `docker-entrypoint.sh`，但 Dockerfile 没 COPY 它 | 无检测 | home-bookshelf L3 |

**C 类的本质**：Docker 的 `WORKDIR /app`（dockerfile_templates.py:558）是一个固定值，但应用代码内部可能有多个不同的 cwd 假设：

- `uvicorn app.main:app` 假设 cwd = `/app`（或 `/app/backend`，取决于 app 包结构）
- `alembic upgrade head` 假设 cwd = alembic.ini 所在目录（因为 `script_location=alembic` 是相对的）
- `sqlite:///./data/bookshelf.db` 假设 cwd = 数据卷挂载点的父目录

**当这三个 cwd 假设互相冲突时**（home-bookshelf 正是如此），lwa 的 Dockerfile 模板无法自动编排出一组一致的 cwd 切换序列。当前模板没有「cwd 编排」这个维度。

### 3.4 D 类：运行时一致性盲区

**定义**：即使 Dockerfile/compose 的配置都正确，lwa 的生命周期管理可能让正确的配置无法生效。

| 问题 | 代码位置 | 表现 | 实证 |
|---|---|---|---|
| 轻量 start 跳过 build | `lifecycle.py:268-272`：`_is_deployed_container` 为 True 时走 `compose up -d`，不 rebuild | 改了 Dockerfile 但容器跑旧镜像 | home-bookshelf L5 |
| 生成配置变化未传导到运行容器 | 轻量 start 跳过 build；现场未留存 Dockerfile/image/container 指纹链 | build 输出大量 CACHED，容器仍是旧 CMD；具体断点待指纹化复现 | home-bookshelf L5 |
| Dockerfile 无条件覆盖 | `dockerfile_templates.py:118` `write_text` 无条件覆盖 | 用户手改被吞 | home-bookshelf L2；BUG-472 |
| DATABASE_URL 不注入 | `compose.py:191`：普通 SQLite 项目不设 `DATABASE_URL` | 应用用默认相对路径，不同 cwd 写不同库 | home-bookshelf L5；BUG-474 |

**D 类的本质**：lwa 的「完整重建」（`host_container`，hosting.py:430-617）和「轻量 start」（`start_container`，hosting.py:620-764）是两条路径，但它们之间的一致性保证不完整：

- `start_container` 在 compose/镜像缺失时回退到 `host_container`（hosting.py:698-703），但**不检测 Dockerfile 内容是否变化**
- `host_container` 的 `generate_dockerfile` 无条件覆盖（hosting.py:497），但**不通知用户覆盖了什么**
- 没有任何环节验证「镜像里的 CMD == 当前 Dockerfile 的 CMD」

### 3.5 E 类：生命周期/数据一致性盲区

**定义**：跨生命周期事件（import 失败清理、rebuild、跨形态迁移）的数据一致性问题。

| 问题 | 代码位置 | 表现 | 实证 |
|---|---|---|---|
| 别名孤儿残留 | `dao.py:301` `delete_instance` 只删主表，级联依赖外键；`connection.py:165` `PRAGMA foreign_keys=ON` 是连接级开关 | 导入失败后别名被占用，`lwa list` 查不到 | home-bookshelf；BUG-473 |
| 跨形态迁移端口丢失 | `importer.py:820-857` 多处端口保留兜底 | update_zip 跨形态时端口登记被清 | BUG-321 / BUG-323 |
| 重建后 containerId 失效 | `importer.py:860-865`：容器源码换 → 清空 containerId/imageId | restart 走轻量路径但旧身份失效 | BUG-112 / DEV-067 |

**E 类**的修复已在 BUG-3xx/4xx 系列中覆盖；BUG-473 与相关别名孤儿问题后续已独立修复。本段保留为历史根因分析，当前同类风险以 #21 的失败回滚完整性为准。

## 4. 为什么「打补丁」修不好

### 4.1 当前的修复模式

观察 BUG-4xx 系列的修复方式，可以看到一个一致的**「针对性 if」模式**：

| BUG | 修复方式 | 代码位置 |
|---|---|---|
| BUG-181（flask+gunicorn 端口不一致） | 新增 `_PYTHON_FRAMEWORK_PRIORITY` 固定优先级 | scanner.py:51-54 |
| BUG-322（Vite 端口覆盖后端） | `_extract_port_from_scripts` 只看 start/dev | scanner.py:565-587 |
| BUG-455（uvicorn target 硬编码） | 新增 `_infer_uvicorn_app_target` | scanner.py:648-666 |
| BUG-198（RUNTIME_ROOT SQLite 路径） | `_detect_sqlite` 检测 `runtime_paths.py` | scanner.py:387-404 |
| alembic CMD `&&`（BUG-471 雏形） | `_python_start_command` 对 alembic 场景 `sh -c` 包裹 | scanner.py:627-629 |

**每个修复都是「遇到一个具体 case → 加一个针对性的 if/分支」**。这种方式的问题不在于修复本身不正确，而在于它**无法覆盖未知的未知**。

### 4.2 累积成本

「针对性 if」模式的累积成本：

1. **scanner.py 越来越复杂**：`_detect_python` 已经有 50+ 行分支（scanner.py:471-517），每加一个特例就更难维护。
2. **测试越来越碎片化**：每个 BUG 一个针对性测试，没有系统性的覆盖矩阵。
3. **认知负担**：新贡献者（或 AI agent）需要理解所有特殊分支的历史背景才能安全修改。
4. **盲区不可见**：每个针对性 if 解决了一个已知 case，但**没有机制发现下一个未知 case**——直到它在生产中暴露。

### 4.3 范式转换 vs 增量补丁

本文档主张：**A/B/C 类失败模式需要范式转换（多候选 + 预检 + 校验），而非更多针对性 if**。但必须诚实说明范式转换的代价：

| 维度 | 打补丁（现状） | 范式转换（本文档） |
|---|---|---|
| 解决已知 case | ✅ 快速、精准 | ⚠️ 需要框架先行 |
| 发现未知 case | ❌ 无机制 | ✅ 预检 + 校验自动发现 |
| 维护成本（长期） | ❌ 线性增长 | ✅ 规则化、可测试 |
| 改动面 | 小（单点） | 大（跨 scanner/importer/lifecycle） |
| 回归风险 | 低 | 中（需完整回归矩阵） |
| 短期交付 | ✅ 可独立合并 | ⚠️ 需分阶段 |

**结论**：不是「范式转换一定比打补丁好」，而是**不同类型的问题需要不同的解决策略**：
- E 类（数据一致性）：继续打补丁（importer.py 已有成熟的防御性代码体系）
- D 类（运行时一致性）：小幅改进（加 Dockerfile 变化检测、镜像 CMD 校验）
- A/B/C 类（识别器的知识盲区）：需要范式转换——这正是本文档的设计目标

### 4.4 最小可行的范式转换：Layer 2 静态预检

范式转换不需要一步到位。**最高性价比的切入点是 Layer 2 静态预检**——不改 scanner 的输出模型，只在识别后、build 前增加一道「配置可行性预检」：

- 不改 `DetectionResult` 的现有字段（向后兼容）
- 不改 scanner 的判定逻辑（不引入回归风险）
- 新增 `preflight.py`，在 `scanner.detect()` 末尾调用
- 预检发现问题时**自动修正**（sh -c 包裹、注入绝对路径、编排 cwd）或标记 warning

**边界**：Gate-A 可独立防住部分命令渲染与路径风险，但它不解决 L1 识别、L2 COPY 子目录，也不保证 L5 镜像/容器已更新。home-bookshelf 的闭环需要 Gate-A + Gate-B + 独立的重建传导校验，不能归功于 Layer 2 单层。

# 第二部分：新范式设计

## 5. 范式对比：即时判定 vs 候选校验

### 5.1 当前范式的时间线

```
用户：lwa import project.zip
  │
  ├─ scanner.summarize()          收集根目录事实（毫秒）
  ├─ scanner.detect()             贪婪即时判定 → 1 个 DetectionResult
  ├─ build_manifest_from_detection()  转为 1 个 InstanceManifest
  ├─ 写入 local-web.json + registry
  └─ import 完成（status=stopped）
       │
用户：lwa start project
  │
  ├─ lifecycle.start_instance()
  │   ├─ host_container()
  │   │   ├─ generate_dockerfile(manifest)     无条件信任 manifest
  │   │   ├─ generate_compose(manifest)        无条件信任 manifest
  │   │   ├─ docker compose build + up         可能失败（L2-L4 卡点）
  │   │   └─ _wait_for_http(host_port)         唯一验证（但只验证端口通）
  │   └─ 失败 → status=failed + last_error
  │
  └─ 用户看到失败 → 手动排查 → 改 manifest → 重试 start
      （循环 N 次，直到所有卡点修完）
```

**问题**：验证发生在流程最末端（`_wait_for_http`），且验证维度极窄（只看 HTTP 200）。前面 5 个转换环节的错误全部堆积到最后才暴露，错误信息（如 `executable file not found`）与根因（识别错误）之间隔了四五层。

### 5.2 新范式的时间线

```
用户：lwa import project.zip
  │
  ├─ Layer 0：evidence_collector.collect()    收集所有事实（毫秒，含子目录）
  ├─ Layer 1：candidate_generator.generate()  证据 → 有序候选列表（毫秒）
  ├─ Layer 2：preflight.check()               候选 → 预检/修正（毫秒）
  │   ├─ CHK-V01~V06：COPY 路径、CMD 安全、DB 路径、alembic cwd ...
  │   └─ 自动修正或淘汰不可行候选
  ├─ build_manifest_from_plans()               top-1 计划 → manifest
  │                                             仅能力等价计划可标记为 alternative
  ├─ 写入 local-web.json + registry
  └─ import 完成（status=stopped，含预检修正记录）
       │
用户：lwa start project
  │
  ├─ lifecycle.start_instance()
  │   ├─ host_container(top-1 候选)
  │   │   ├─ docker compose build + up
  │   │   └─ 存活探针 + 项目声明/证据发现的必选探针
  │   ├─ 失败？
  │   │   ├─ 记录失败诊断并回滚本次 attempt
  │   │   ├─ 回滚成功且无不可逆外部副作用？
  │   │   │   ├─ 否 → status=failed + 完整诊断报告（Layer 4）
  │   │   │   └─ 是 → 查找能力契约完全等价的 alternative
  │   │   │       ├─ 默认 confirm → 等待用户确认
  │   │   │       ├─ auto-equivalent → 切换并重试（Layer 3）
  │   │   │       └─ 无等价计划 → status=failed（Layer 4）
  │   │   └─ 成功 → status=running
  │   └─ 成功 → 同步别名 + 完成
  │
  └─ 用户看到成功（或失败时看到精确诊断，知道每个候选失败在哪一步）
```

**核心差异**：

1. **验证前移**：Layer 2 静态预检在 import 阶段就修正大部分配置错误（L2-L4），不必等到 build 才暴露
2. **多计划**：不再赌博式地选一个结论；先区分协作组件与功能等价的替代计划，只在能力契约相同且可回滚时降级
3. **诊断闭环**：即使全部候选失败，也输出每个候选失败在哪一步的精确诊断

### 5.3 不是所有项目都需要走完整流程

新范式的成本控制关键：**简单项目快速通过，复杂项目才深入校验**。

| 项目类型 | Layer 0 | Layer 1 | Layer 2 | Layer 3 | 总耗时 |
|---|---|---|---|---|---|
| 纯静态 HTML（根目录 index.html） | 毫秒 | 1 候选（static, confidence=high） | 直接过（无修正） | start 时执行轻量存活探针 | ≈ 当前 |
| 根目录 Flask（requirements.txt 在根） | 毫秒 | 1 候选（python, confidence=high） | COPY 路径通过 | start 时执行轻量存活/就绪探针 | ≈ 当前 |
| 根目录 Vite 前端 | 毫秒 | 1 候选（frontend-static, high） | 直接过 | start 时执行轻量存活探针 | ≈ 当前 |
| home-bookshelf（backend/+frontend/） | 毫秒 | 1 个全栈部署计划（frontend 构建组件 + python@backend 运行组件） | 预检计划的产物传递、cwd、DB 路径 | start 时执行必选验证 | +构建时间 |
| patent-disclosure（npm workspaces） | 毫秒 | 2 候选（node@webpage, pending@desktop） | 预检通过 | start 必验；不确定或失败时进入完整验证/回退流程 | +分钟（仅完整验证时） |

## 6. 五层流水线详设

### 6.1 模型总览

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 0：证据收集            毫秒级    纯文件操作            │
│  evidence_collector.collect(root) → ProjectEvidence          │
│  目标：收集所有客观事实，零解释                                │
│  扩展：子目录探测、alembic 配置解析、entrypoint 脚本检测       │
└──────────────────────────┬──────────────────────────────────┘
                           │ ProjectEvidence
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Layer 1：候选生成            毫秒级    规则推理              │
│  candidate_generator.generate(evidence) → list[DeploymentPlan] │
│  目标：证据 → 部署拓扑 + 功能等价的替代候选          │
│  规则：子目录布局、monorepo、传统单根目录                      │
└──────────────────────────┬──────────────────────────────────┘
                           │ list[DeploymentPlan]
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Layer 2：静态预检            毫秒级    可行性校验 + 自动修正  │
│  preflight.check(plans, evidence) → PreflightResult          │
│  目标：不 build，快速淘汰/修正不可行候选                       │
│  检查：COPY 路径、CMD 安全、DB 路径、alembic cwd、entrypoint  │
│  产出：修正后的候选列表 + warnings + 修正动作记录              │
└──────────────────────────┬──────────────────────────────────┘
                           │ 检查后的 list[DeploymentPlan]
                           ▼
              ┌─ 唯一可行计划 ─→ 写入 manifest；start 时仍执行必选验证
              │
              ├─ 多个功能等价计划 → top-1 入 manifest，其余才可进入 fallback
              │                         start 失败时按能力契约降级（Layer 3）
              │
              └─ 零可行候选 ───→ pending + 诊断报告（Layer 4）
```

### 6.1.1 两个必须分开的概念

| 概念 | 定义 | home-bookshelf 中的例子 |
|---|---|---|
| **部署组件（component）** | 共同完成一个业务系统的构建或运行单元，彼此不可替代 | `frontend/` 负责构建 SPA，`backend/` 负责运行 API、迁移和托管产物 |
| **替代候选（alternative）** | 交付相同必要能力的另一套部署计划，只有能力契约等价时才可 fallback | 「LWA 模板生成容器」与「使用经验证的项目 Dockerfile」可能成为两个替代计划 |

**硬性约束**：不得把「后端容器」降级为「前端静态站」并仍声明部署成功。静态页可以作为识别诊断线索，但不是全栈计划的运行时 fallback。

### 6.2 Layer 0：证据收集

#### 目标

收集项目目录的所有客观事实，**零解释**——不做任何推理判断，只记录「什么文件存在」「什么配置写了什么」。推理是 Layer 1 的事。

#### 数据结构

```python
@dataclass
class ProjectEvidence:
```

```python
def collect(root: Path) -> ProjectEvidence:

        if subdir.is_dir():
            signal = _probe_subdir(subdir, subdir_name)
            if signal.has_requirements or signal.has_package_json or signal.has_pyproject:
                evidence.subdir_signals[subdir_name] = signal

    # 3. 依赖收集（根目录 + 主子目录）
    # 复用 scanner._collect_python_deps / _read_package_json
    ...

    # 4. 入口候选探测（替代 _infer_uvicorn_app_target 的硬编码布局）
    # 扫描根目录和子目录下的 main.py / app.py / server.js ...
    ...

    # 5. alembic.ini 解析（C 类修复）
    for path in _find_alembic_ini(root):
        config = _parse_alembic_ini(path)
        evidence.alembic_config = config

    # 6. entrypoint 脚本检测
    for name in ("docker-entrypoint.sh", "entrypoint.sh", "start.sh"):
        path = _find_anywhere(root, name, max_depth=2)
        if path:
            evidence.entrypoint_scripts.append(path)

    # 7. 项目自带 Dockerfile/compose（D 类修复）
    evidence.project_dockerfile = _find_dockerfile(root)
    evidence.project_compose = _find_compose(root)

    # 8. 数据库配置尽力解析（C 类修复）
    evidence.database_config = _parse_database_config(root)

    return evidence
```

**采集成本控制**：
- 子目录探测限制在 `COMMON_SUBDIRS` 列表 + 最多 2 层深度
- 跳过 `node_modules` / `.git` / `__pycache__` / `dist` / `build` 等噪音目录
- 所有操作都是 `Path.is_file()` / `Path.iterdir()` / 文件读取，无网络/无 Docker

### 6.3 Layer 1：候选生成

#### 目标

根据 Layer 0 的证据，先生成**部署计划（DeploymentPlan）**，再在计划内表达需要协作的组件。只有必要能力等价的多个计划，才是可互相降级的替代候选。

#### 数据结构

```python
@dataclass
class CapabilityContract:
    """部署成功必须保留的业务能力。"""
    serves_ui: bool = False
    serves_api: bool = False
    requires_database: bool = False
    requires_migrations: bool = False
    required_probes: list["ProbeSpec"] = field(default_factory=list)

    @property
    def required_capabilities(self) -> set[str]:
        """由结构化标志派生，避免维护第二份能力真相源。"""
        pairs = {
            "ui": self.serves_ui,
            "api": self.serves_api,
            "database": self.requires_database,
            "migrations": self.requires_migrations,
        }
        return {name for name, required in pairs.items() if required}


@dataclass
class DeploymentPlan:
    """一套完整部署拓扑；内部组件是合作关系，不是 fallback 关系。"""
    plan_id: str
    components: list["DeploymentComponent"]
    capability_contract: CapabilityContract
    confidence_tier: str
    reasoning: list[str]
    evidence_refs: list[str]


@dataclass
class DeploymentCandidate:
    """兼容现有 Gate-B 实现的单组件候选。

    过渡期保留；Gate-C 不得只根据该结构自动降级。
    """
    # 核心分类（与 DetectionResult 对齐）
    kind: Kind                              # STATIC / NODE / PYTHON
    runtime: Runtime                        # SHARED_STATIC / DOCKER_COMPOSE
    serving_mode: ServingMode               # SHARED_STATIC / CONTAINER
    form: str                               # static / frontend-static / backend-container / fullstack-sqlite
    resource_profile: ResourceProfile       # TINY / SMALL / MEDIUM

    # 部署参数
    entry: EntryConfig                      # install / build / start
    internal_port: int | None
    source_subdir: str | None               # 源码子目录（如 "backend"），None = 根目录
    database: DatabaseConfig | None

    # 命令语义（Gate-C 前必须结构化）
    workdir: str = "/app"
    environment: dict[str, str] = field(default_factory=dict)
    pre_start: list["CommandSpec"] = field(default_factory=list)
    capability_contract: CapabilityContract | None = None

    # 候选元数据
    confidence_tier: str                    # "primary" / "alternate" / "fallback"
    reasoning: list[str]                    # 为什么生成这个候选（证据 → 结论的推理链）
    evidence_refs: list[str]                # 支撑证据的字段名（可追溯）
```

#### 候选生成规则表

以下规则按优先级排列。Gate-B 当前仍输出扁平 `DeploymentCandidate`；本表增加「角色」列，明确 Gate-C 收口时必须如何将它们转换为 `DeploymentPlan`，并由计划执行器消费。

| 规则 | 触发条件 | 输出 | 角色 | confidence_tier |
|---|---|---|---|---|
| **R-python-subdir** | `backend/server/api` 有 Python Web 框架依赖 | python/docker-compose，`source_subdir="backend"` | 运行组件；如存在前端则纳入同一全栈计划 | primary |
| **R-python-root** | 根目录有 Python Web 框架依赖 | python/docker-compose | 运行组件 | primary |
| **R-node-monorepo** | 根 package.json 有 `workspaces` | node/docker-compose | 运行组件或构建组件，由包分类决定 | primary |
| **R-node-root** | 根目录有 NODE_BACKEND | node/docker-compose | 运行组件 | primary |
| **R-frontend-subdir** | `frontend/client/web` 有 NODE_FRONTEND + build | frontend build | 若存在后端：同一计划的构建组件；否则可独立成为静态计划 | primary/alternate |
| **R-frontend-root** | 根目录有 NODE_FRONTEND + build | frontend-static | 无后端时是独立计划 | primary |
| **R-static** | 有 index.html，且无更强工程信号 | static/SHARED_STATIC | 独立静态计划 | primary |
| **R-static-diagnostic** | 有 index.html，且同时存在后端信号 | static 诊断线索 | **不持久化为运行时 fallback** | diagnostic |

**置信度分组规则**：
- `primary`：有明确的框架依赖信号（NODE_BACKEND / PYTHON_WEB）+ 完整的工程文件
- `alternate`：有部分信号但不完整（如子目录有前端但根目录也可能有后端）
- `fallback`：功能等价的替代部署计划；是否可降级由 `capability_contract` 决定，不由置信度单独决定
- `diagnostic`：只用于解释「为什么旧 scanner 会判为 static」，不参与自动启动

**home-bookshelf 的候选生成示例**：

```
证据：

  subdir_signals["frontend"]: has_package_json=True, node_deps={vue, vite}

收敛后：

```

#### 多候选决策矩阵

| 可行部署计划数 | 行为 |
|---|---|
| 0 | pending + 诊断 |
| 1 | 该计划入 manifest；其内组件按拓扑协作执行 |
| ≥2，且能力契约不同 | **不自动选**；pending + 用户选择指引 |
| ≥2，且能力契约相同 | 可按确定性评分选 top-1；其余只在事务回滚可用时进入 fallback |

### 6.4 Layer 2：静态预检

#### 目标

不 build，在毫秒级内检查每个候选的**静态配置可行性**，修正证据充分且可无损修正的问题，淘汰明确不可行的候选。它可快速阻断 COPY、简单命令渲染和已知 cwd/DB 风险，但不代替构建、镜像传导、运行时探针和数据安全验证。

#### 预检项清单

每项预检的格式：`检查ID | 检查目标 | 检查逻辑 | 自动修正策略 | 对应 BUG`

##### CHK-V01：COPY 源路径文件存在性

| 项 | 内容 |
|---|---|
| **检查目标** | Dockerfile 的 `COPY current/<req_file>` 对应的文件在构建上下文中存在 |
| **检查逻辑** | 从候选的 `entry.install` 解析 requirements 文件名（复用 `_extract_requirements_file`），检查 `source_dir / source_subdir / req_file` 是否存在 |
| **自动修正** | 若 `source_subdir` 为 None 但文件在子目录 → 修正 `source_subdir` 为对应子目录 |
| **不可修正** | 文件完全不存在 → rejected |
| **对应 BUG** | home-bookshelf L2；DEV-105 |

##### CHK-V02：CMD shell 操作符安全

| 项 | 内容 |
|---|---|
| **检查目标** | `entry.start` 不含会被 `_to_exec_form` 拆碎的 shell 操作符 |
| **检查逻辑** | `re.search(r'[&\|;<>$`\(\)]', entry.start)` 或 `'$(' in entry.start` |
| **Gate-A 战术性修正** | 模板渲染时输出 exec 形式 `['sh', '-c', '<原命令>']`，避免把操作符当普通 argv |
| **限制** | 不用正则改写任意复杂 shell；原命令含嵌套引号、重定向或多阶段时只告警。Gate-C 改用 `CommandSpec(argv/shell/workdir/env)` |
| **对应 BUG** | BUG-471；home-bookshelf L3 |

##### CHK-V03：数据库路径与 volume 一致性

| 项 | 内容 |
|---|---|
| **检查目标** | 应用的数据库路径与 compose volume 挂载点一致（都在 `/app/data` 下） |
| **检查逻辑** | 若 `evidence.database_config.is_relative=True` → 检查应用的默认 DB 路径在不同 cwd 下是否会解析到非 `/app/data` 的位置 |
| **自动修正前提** | 已确认应用读取 `DATABASE_URL`，已解析原数据库文件名，目标位于持久卷，且不会切换到新空库 |
| **自动修正** | 满足上述前提时才注入 `DATABASE_URL=sqlite:////app/data/<db_filename>`；否则 warning/pending，由用户确认配置键和目标文件 |
| **对应 BUG** | BUG-474；home-bookshelf L5 |

##### CHK-V04：alembic script_location 可达性

| 项 | 内容 |
|---|---|
| **检查目标** | `alembic upgrade head` 能找到 `script_location` 指向的迁移脚本目录 |
| **检查逻辑** | 若 `evidence.alembic_config` 不为 None：检查 `script_location` 是否相对路径；若是，验证 `<alembic.ini 所在目录>/<script_location>` 是否存在；若 `entry.start` 含 `alembic` 且 cwd 与 alembic.ini 目录不一致 → 标记风险 |
| **自动修正** | 生成结构化 `pre_start` 步骤，显式设定 `workdir=<source_subdir>`；主进程使用自己的 `workdir` |
| **兼容期限制** | Gate-A 现有字符串 `cd ... &&` 编排只覆盖已知简单形态，必须保留 warning，不宣称能普遍解析 shell |
| **对应 BUG** | BUG-474；home-bookshelf L4 |

##### CHK-V05：entrypoint 脚本 COPY 完整性

| 项 | 内容 |
|---|---|
| **检查目标** | 若 `entry.start` 引用了 entrypoint 脚本（如 `docker-entrypoint.sh`），该脚本在 Dockerfile 的 COPY 范围内 |
| **检查逻辑** | 从 `entry.start` 提取脚本名，检查 `evidence.entrypoint_scripts` 是否包含它；若包含，检查 Dockerfile 模板是否会 COPY 它（当前模板 `COPY current/ ./` 会包含，但若用户改了模板需检查） |
| **自动修正** | 脚本存在但 Dockerfile 不 COPY → 追加 COPY 行；脚本不存在 → rejected |
| **对应 BUG** | home-bookshelf L3 |

##### CHK-V06：项目自带 Dockerfile 检测

| 项 | 内容 |
|---|---|
| **检查目标** | 检测项目自带 Dockerfile，避免 lwa 覆盖时无提示 |
| **检查逻辑** | `evidence.project_dockerfile` 不为 None |
| **处理方式** | **不自动修正**（涉及产品定位决策）；标记 warning + 事件记录：「检测到项目自带 Dockerfile（<path>），lwa 将生成自己的 Dockerfile（可被覆盖）。如需使用项目自带 Dockerfile，请 XXX」 |
| **对应 BUG** | BUG-472；home-bookshelf L2 |

#### home-bookshelf 的 Layer 2 走查

对 home-bookshelf 的 primary 候选（python/docker-compose, source_subdir=backend）执行预检：

| 预检 | 输入 | 结果 | 修正动作 |
|---|---|---|---|
| CHK-V01 | `COPY current/backend/requirements.txt` | ✅ 文件存在 | 无需修正（source_subdir 已正确设置） |
| CHK-V02 | `entry.start = "alembic upgrade head && uvicorn ..."` | ⚠️ 含 `&&` | **自动修正**：包裹 `sh -c 'cd backend && alembic upgrade head && cd /app && exec uvicorn app.main:app ...'` |
| CHK-V03 | `database_config.is_relative=True` | ⚠️ 相对路径 | 确认应用读取 `DATABASE_URL` 且保留 `bookshelf.db` 后，注入绝对路径 |
| CHK-V04 | `alembic_config.script_location=alembic, subdir=backend` | ⚠️ cwd 不一致 | 将 migration 建模为 `pre_start(workdir="/app/backend")`，不在主命令中往返 `cd` |
| CHK-V05 | `entry.start` 引用 `docker-entrypoint.sh` | ⚠️ 脚本在 `backend/` | **自动修正**：sh -c 包裹后不再直接引用脚本（或追加 COPY） |
| CHK-V06 | `project_dockerfile = backend/Dockerfile` | ⚠️ 项目自带 | **警告**（不修正）：记录事件 |

**目标结果**：部署计划被调整为两个命令阶段：

```text
pre_start:
  workdir: /app/backend
  argv: ["alembic", "upgrade", "head"]

start:
  workdir: /app
  argv: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

environment:
  DATABASE_URL: sqlite:////app/data/bookshelf.db
```

**static 诊断线索的处理**：
- CHK-V01：static 无 COPY requirements → N/A
- 其他项 N/A
- 发现 `evidence.subdir_signals["backend"]` 有 Python 依赖 → 标记「静态结果不具备 API/DB 能力」
- 与 fullstack `capability_contract` 不等价 → 不写入运行时 fallback

**最终**：home-bookshelf 收敛为一个全栈部署计划，其中的命令、路径和产物传递通过预检。Layer 2 只证明静态可行性，不替代 start 时的构建、迁移、HTTP 与业务探针。

### 6.5 Layer 3：实证校验

#### 目标

在 `lwa start` 中实际执行 build + up + 必选探针，验证部署计划是否交付了 `CapabilityContract` 声明的能力。

**术语收敛**：容器的基础 build/up 本来就发生在 start 阶段；本文所说的 Layer 3，特指「可判定成败的验证结果 + 受约束的候选切换」，不再把单纯 `docker compose up` 称为已通过 Layer 3。

#### 触发条件

| 条件 | 是否触发 Layer 3 |
|---|---|
| import 完成 | ❌ 默认不 build；只保存静态预检结果 |
| `lwa import --verify` | ⚠️ 可选执行，但不改变默认 import 性能语义 |
| 任何部署计划首次 `lwa start` | ✅ 必须产生 `VerificationResult` |
| 运行中实例轻量 start | ✅ 至少执行必选存活探针；配置/镜像指纹变化时不允许走轻量路径 |
| top-1 失败 + 存在能力等价 fallback | ⚠️ 先回滚，再按用户策略尝试；非等价计划不得自动切换 |

#### 与现有 `host_container` 的关系

实施前的 `host_container`（历史锚点 hosting.py:430-617）只做 build + up，并在 best-effort HTTP 检查前写入 `RUNNING`。修订版 Gate-C 后续已完成下面第 1～4 项；#21 表明第 3 项对路径别名元数据和网关片段的覆盖仍存在新增回归缺口：

1. build/up 成功后进入 `VERIFYING`，不立即写 `RUNNING`。
2. 必选探针通过才进入 `RUNNING`；只有可选探针失败时可进入 `DEGRADED`。
3. 验证失败时先回滚容器、端口、生成文件和 manifest 选中状态。
4. 只有下一计划的 `CapabilityContract` 与当前计划等价，且回滚成功，才允许切换。

#### 成功谓词

```text
plan_succeeded =
    build_succeeded
    AND start_succeeded
    AND all(required_probe.passed)
    AND capabilities_observed >= capability_contract.required_capabilities
```

- **基础存活探针**：必选，证明进程存活且目标端口可达，但不证明业务完整。
- **应用就绪探针**：项目声明或从可靠证据发现时为必选，例如 `/health` 预期 2xx。
- **API 业务探针**：只有已知路径、方法和预期状态时才可作为成功门槛。猜测 `/api/` / `/api/v1/` 只能产生诊断，404/401 不能单独判定部署失败。
- **数据库/迁移能力**：若契约要求，必须由迁移命令退出码或项目健康接口证明，不得从首页 200 推断。

#### 候选切换事务

| 阶段 | 最低要求 |
|---|---|
| Prepare | 快照 manifest、选中计划、端口登记和生成文件指纹；声明 migration/外部写入等副作用及其可恢复方式 |
| Execute | 为当前尝试使用独立 attempt/build ID，不覆盖上一次成功记录 |
| Verify | 按上述成功谓词评估，记录每个探针的证据 |
| Commit | 只有验证成功后才写入选中计划、容器 ID、网络入口和 `RUNNING` |
| Rollback | 回滚范围默认仅含本次容器、端口、manifest 和生成文件；数据库 schema/data、外部服务写入不因容器 down 自动恢复，必须单独记录结果 |

**回滚边界**：`rollback_succeeded` 只表示已声明的回滚步骤全部成功，不得笼统解释为“系统没有任何副作用”。若 attempt 可能执行数据库迁移、队列发布或外部 API 写入，则只有满足下列任一条件，才可把 `automatic_fallback_safe` 置为 `true`：

1. 副作用运行在可丢弃的隔离环境；
2. 已有可验证的事务回滚；
3. 已从本次快照恢复，并通过恢复后探针。

否则，即使容器和 manifest 已恢复，也必须停止自动 fallback，输出人工处置提示。生产数据默认不自动删除或反向迁移。

#### 成本控制

- **build 失败快速退出**：docker build 失败立即标记候选失败，不等 health check
- **超时**：单计划 Layer 3 超时（如 5 分钟）→ 标记失败 → 完成回滚与副作用评估；仅在满足等价 fallback 条件时才尝试下一计划
- **缓存**：只有 source hash + plan hash + generated-config hash + image ID 都未变时，才可复用上次实证结果；轻量 start 仍做存活探针
- **最大尝试次数**：最多尝试 N 个候选（默认 3），超过则进 Layer 4

#### 数据结构

```python

    plan_id: str
    build_succeeded: bool
```

#### 目标

### 8.3 scanner.py 重构策略（Gate-B）

**不重写 scanner.py，而是分层编排**：

```python
# scanner.py Gate-B 重构后的 detect()（伪代码）

class Scanner:
    def detect(self, project_dir: Path) -> DetectionResult:
        # Gate-A 阶段：保持现有逻辑 + preflight
        # Gate-B 阶段：改为编排 Layer 0-2

        # Layer 0：证据收集
        from local_webpage_access.evidence_collector import collect
        evidence = collect(project_dir)

        # Layer 1：候选生成
        from local_webpage_access.candidate_generator import generate_candidates
        candidates = generate_candidates(evidence)

        # Layer 2：静态预检
        from local_webpage_access.preflight import check_candidates
        checked = check_candidates(candidates, evidence)

        # 构造 DetectionResult（向后兼容）
        result = DetectionResult(evidence=evidence, candidates=checked)
        if checked:
            top = checked[0]  # top-1 候选
            # 映射到旧字段
            result.kind = top.kind
            result.runtime = top.runtime
            result.servingMode = top.serving_mode
            result.entry = top.entry
            result.form = top.form
            result.confidence = "high" if top.confidence_tier == "primary" else "medium"
            result.pending = False
        else:
            result.pending = True
            result.notes.append("无可行部署候选")

        return result
```

**关键设计**：现有 `_detect_python` / `_detect_node` / `_detect_static` **不删除**——它们被 `candidate_generator` 的规则封装。Gate-B 可以先把现有 `_detect_*` 的逻辑搬到 `candidate_generator` 的对应规则函数里，保持行为等价。

### 8.5 lifecycle.py 降级策略（Gate-C）

```python
# lifecycle.py start_instance（Gate-C 改动点，伪代码）

def start_instance(workspace, config, registry, instance_id, fallback_policy="confirm"):
    with instance_lock(workspace, instance_id):
        manifest = _load(workspace, instance_id)

        plans = _load_validated_plans(manifest)
        primary = _select_primary(plans)
        result = _execute_verify_transaction(primary)
        if result.overall_status in ("passed", "degraded"):
            return _commit_verified_plan(manifest, primary, result)

        rollback = _rollback_attempt(result.attempt_id)
        if not rollback.succeeded or not result.automatic_fallback_safe:
            raise _build_diagnosis_error(instance_id, result, rollback=rollback)
        equivalents = [
            plan for plan in plans
            if plan.plan_id != primary.plan_id
            and plan.capability_contract == primary.capability_contract
        ]
        if not equivalents:
            raise _build_diagnosis_error(instance_id, result, equivalents)

        if fallback_policy == "confirm":
            # 交互式 CLI/管理页在上层展示等价计划并等待确认；非交互调用
            # 返回结构化 FallbackConfirmationRequired，不把它伪装成部署诊断失败。
            approved = _request_confirmation_or_raise(instance_id, result, equivalents)
            equivalents = [approved]
        elif fallback_policy != "auto-equivalent":
            raise ValueError(f"unknown fallback policy: {fallback_policy}")

        for fallback in equivalents:
            retry = _execute_verify_transaction(fallback)
            if retry.overall_status in ("passed", "degraded"):
                return _commit_verified_plan(manifest, fallback, retry)
            rollback = _rollback_attempt(retry.attempt_id)
            if not rollback.succeeded or not retry.automatic_fallback_safe:
                raise _build_diagnosis_error(instance_id, retry, rollback=rollback)

        raise _build_diagnosis_error(instance_id, result, equivalents)
```

**默认策略**：`fallback_policy="confirm"`。交互式 CLI/管理页由上层展示等价计划并等待确认；非交互调用返回结构化 `FallbackConfirmationRequired`，由调用方决定是否携带明确的计划选择重试。该结果不是部署成功，也不应被折叠为普通诊断失败。只有用户显式选择 `auto-equivalent`，且能力契约完全等价、回滚已成功时，才允许自动切换。

```python
# preflight.py check_and_fix()（Gate-A 版本，伪代码）

def check_and_fix(result: DetectionResult, project_dir: Path) -> DetectionResult:
    """对识别结果执行静态预检，自动修正配置问题。"""
    if result.pending or result.kind is None:
        return result  # 未识别，不预检

    fixes = []

    # CHK-V02：CMD shell 操作符安全
    if result.entry.start:
        fixed_start, v02_fix = _check_cmd_safety(result.entry.start)
        if v02_fix:
            result.entry.start = fixed_start
            fixes.append(v02_fix)

    # CHK-V03：数据库路径一致性
    if result.hasDatabase and result.database:
        v03_fix = _check_db_path(result, project_dir)
        if v03_fix:
            fixes.append(v03_fix)

    # CHK-V04：alembic script_location（若检测到 alembic.ini）
    if project_dir:
        v04_fix = _check_alembic_cwd(result, project_dir)
        if v04_fix:
            fixes.append(v04_fix)

    # CHK-V06：项目自带 Dockerfile
    project_dockerfile = _find_project_dockerfile(project_dir)
    if project_dockerfile:
        result.notes.append(
            f"⚠️ 检测到项目自带 Dockerfile（{project_dockerfile}），"
            f"lwa 将生成自己的 Dockerfile"
        )

    # 记录修正到 notes
    if fixes:
        result.notes.append(f"预检自动修正 {len(fixes)} 项：{'; '.join(fixes)}")

    return result
```

|---|---|

## 13. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|
| **多候选 build 耗时** | Gate-C 的 Layer 3 最坏要 build N 个候选 | 中 | Layer 2 预检淘汰大部分错误候选；多数项目只有 1 个候选活到 Layer 3；设超时 + 最大尝试次数 |
| **非等价降级产生假成功** | 全栈项目只启动静态首页却被标记 running | 高 | 组件/替代计划分建模；CapabilityContract 必须等价；新增全栈不降 static 的回归 |
| **部分启动污染下一候选** | 端口、容器、manifest 或生成文件残留，诊断失真 | 高 | Prepare/Execute/Verify/Commit/Rollback 事务模型；故障注入覆盖每个阶段 |
| **迁移或外部写入无法完整回滚** | schema/data/消息/API 副作用残留，后续计划在污染状态中运行 | 高 | 显式副作用台账；仅隔离环境、事务回滚或快照恢复验证通过时允许自动 fallback，否则停止并提示人工处置 |
| **预检自动修正改变用户预期** | 用户 manifest 的 entry.start 被静默修改 | 中 | 修正记录写入 notes + registry 事件；`lwa scan --dry-run` 可预览修正；用户可 `--no-preflight` 跳过 |
| **scanner 重构引入回归** | Gate-B 的 detect() 重构可能破坏 470+ 个 BUG 修复的特殊分支 | 高 | 分阶段重构：先把现有 `_detect_*` 搬到 candidate_generator（行为等价），再逐步增强；完整回归矩阵 |
| **候选列表对 manifest/CLI 的影响** | manifest 增加 deployment_candidates 字段，CLI/管理页需适配 | 中 | 新字段可选，默认空列表；旧 manifest 可加载（Field default_factory=list）；CLI/管理页按需适配 |
| **与 IMP-057 的融合冲突** | IMP-057 的 package_classifier 与 candidate_generator 的接口不匹配 | 低 | IMP-057 的规则集作为 candidate_generator 的插件，接口在 Gate-B 设计时对齐 |
| **子目录探测性能** | evidence_collector 扫描多个子目录可能变慢 | 低 | 限制 COMMON_SUBDIRS 列表 + 2 层深度 + 跳过噪音目录；毫秒级 |
| **预检修正的确定性** | 同一项目的预检修正结果必须确定（可测试） | — | 预检逻辑尽量保持纯函数；涉及文件系统/环境时将证据快照作为显式输入 |
| **SQLite 自动注入切换到错误数据库** | 应用忽略变量、原文件名丢失或连到新空库 | 中 | 只在确认配置消费点、文件名和持久卷映射时自动修正；否则 warning/pending |
| **字符串 shell 自动改写破坏语义** | 嵌套引号、重定向、变量展开或信号传递错误 | 中 | Gate-A 只处理有界形态；Gate-C 改用 CommandSpec，复杂 shell 不自动改写 |
| **诊断报告的信息过载** | Layer 4 输出太多信息让用户困惑 | 中 | 分级展示：先摘要（哪个候选成功/失败），再详情（每步诊断）；CLI 默认摘要，`--verbose` 展开详情 |

## 14. 已定案决策与开放问题

本节同时保留已定案结论和仍可微调的实现问题。标记「已定案」的约束是 Gate-C 开工前提，不得在实现期默认改回无约束自动降级。

### 14.1 候选降级是自动还是需用户确认？（已定案）

**问题**：Gate-C 的 Layer 3，top-1 候选 build 失败后，自动尝试 fallback 还是问用户？

**定案**：默认需用户确认。只有同时满足「能力契约完全等价」、「上一尝试回滚成功」与「用户已开启 `auto-equivalent`」时才自动降级。非等价计划（如 fullstack → static）永不自动降级。

### 14.2 Layer 3 在 import 时触发还是 start 时触发？（已定案）

**问题**：实证校验（build + health check）应该在 import 时做，还是推迟到 start 时？

**选项**：
- **A import 时**：import 即验证，用户体验好（导入后就知道能不能跑）；但 import 变慢（分钟级）
- **B start 时**：import 保持毫秒级；start 时才验证；失败时降级
- **C 可选**：`lwa import --verify` 触发；默认不验证

**定案**：默认在 start 时执行；`import --verify` 只是可选入口。首次 start 必须产生 VerificationResult，轻量 start 也至少执行存活探针。

### 14.3 预检修正应写回 manifest 还是临时生效？

> **2026-08-31 状态**：本节与 §14.4 是非阻塞的演进选项，不属于已完成 Gate-C 的欠账；仅在继续扩展对应能力时重新拍板。

**问题**：Layer 2 自动修正的 entry.start（如 sh -c 包裹），是写回 manifest 持久化，还是只在 build 时临时修正？

**选项**：
- **A 写回 manifest**：manifest 反映真实部署配置；用户可见；但修改了用户的 manifest
- **B 临时生效**：manifest 保持原始识别结果；修正只在 generate_dockerfile 时应用；用户看到的 manifest 是「识别结果」而非「部署配置」
- **C 写回 + 标注**：写回 manifest 但标注 `preflight_adjusted=True`，用户可还原

**倾向**：C（写回 + 标注）。同时保留 `detected_value`、`effective_value`、修正规则 ID 和 evidence hash，既让 manifest 反映真实部署配置，又能追溯与重算，避免只留下不可逆的字符串改写结果。

### 14.4 COMMON_SUBDIRS 列表的范围

**问题**：`evidence_collector` 的 `COMMON_SUBDIRS` 应该包含哪些子目录名？

**候选列表**：
- 确定包含：`backend`, `server`, `api`, `frontend`, `client`, `web`
- 可选：`app`（可能与 Python app 包混淆）、`ui`、`static`（可能是静态产物而非源码）

**倾向**：先包含确定列表（6 个），根据实际案例扩展。`app` 单独处理（检测它是否是 Python 包目录 vs 工程子目录）。

### 14.5 `_to_exec_form` 的修正策略

**问题**：检测到 shell 操作符后，是包裹 `sh -c '...'`（shell 形式），还是用 `["sh", "-c", "..."]`（exec 形式但通过 sh）？

**定案（Gate-A）**：已识别的简单复合命令用 exec 形式 `["sh", "-c", "..."]`，并避免双重包裹。

**定案（Gate-C）**：不再扩大字符串正则改写范围；使用 `CommandSpec` 显式表达 `argv/shell/workdir/env`。无法无损结构化的复杂 shell 只告警或 pending。

## 附录 B：术语表

| 术语 | 定义 |
|---|---|
| **即时贪婪判定** | 当前 scanner 的范式：遇到第一个匹配规则就下结论，不回头 |
| **部署计划** | 能交付一组能力契约的完整部署拓扑，内部可含多个协作组件 |
| **部署组件** | 计划中的构建或运行单元，例如 frontend-build 与 python-container；组件之间不是 fallback 关系 |
| **替代候选** | 能力契约等价的另一部署计划；只有等价且可回滚时才可自动降级 |
| **能力契约** | 部署成功必须保留的 UI/API/DB/迁移/探针等能力集合 |
| **预检** | 在 build 前检查配置可行性，自动修正或淘汰不可行配置 |
| **实证校验** | 实际 build + start + 必选探针，按成功谓词验证能力契约 |
| **布局** | 项目源码的组织结构（子目录、monorepo、前后端分仓）；旧 scanner 不感知，Gate-B 已纳入证据与候选生成 |
| **置信度层级** | primary（高置信）/ alternate（中）/ fallback（低/兜底） |
| **workdir 编排** | 为 migration/start 等命令阶段显式指定工作目录，不依赖在同一 shell 中往返 `cd` |
| **假信号** | lwa 报告「成功执行了某操作」，但该操作的实际效果与预期不符；需通过指纹、image ID、Config.Cmd 和必选探针定位传导断点 |

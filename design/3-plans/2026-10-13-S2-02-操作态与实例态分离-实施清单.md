# S2-02 操作态与实例态分离 — 实施清单

- 日期：2026-10-13
- 工作包：WBS S2-02（台账 BUG-750 / issue #57-2、BUG-759 / N6，决策 D4）
- 前置：S2-01 统一停机语义（已合入主线，gate 全绿）

## 1. 目标与规则

实例 `status` 只由观测结果决定（running/stopped/failed，failed 表示「未在服务」）。
构建、排队、验证失败一律只写 `lastOperation`（操作态）与 `lastError`，不得改写实例
观测状态。排队超时、构建失败时仍在服务的旧容器不再被误标 FAILED。

## 2. lastOperation 存储选型

**选型：manifest 新增 `lastOperation` 字段 + registry `instances` 表新增
`last_operation_json` 列（schema v6），两处在每次写入时同步。**

理由：

1. WBS 两个候选中，「builds 表 + 事件派生」读取方需要按实例回放 builds/events
   再推断最近一次操作结果，派生逻辑脆弱（builds 行有孤儿、遮蔽等历史问题，
   见 BUG-048/BUG-119），且无法表达「排队超时」这类没有 builds 行的操作。
2. 项目已有 JSON 列先例（`stack_json`、`options_json`、`payload_json`），
   `last_operation_json` 与 manifest 字段 `{kind, status, buildId, startedAt,
   finishedAt, error, source}` 形状一一对应，一次 ALTER 即可，无需七列宽表。
3. registry 列是 API/CLI 列表视图的权威读取点（`status.py` 快照直接读行，不依赖
   manifest 可读）；manifest 字段保留给 skill / 人工读 `local-web.json` 的契约
   场景。写入统一经 `upsert_from_manifest` 与 `update_last_operation`，
   两处不会漂移。

`lastOperation.status` 词汇：`queued` / `building` / `succeeded` / `failed` /
`cancelled`（`cancelling` 为内存/DB 任务行中间态，不写入实例操作态）。
`kind` 词汇：`build`（构建队列）、`rebuild` / `deploy`（容器/前端托管流程，
视是否有旧容器而定）。

## 3. 字段 → 权威来源 → 写入方 → 读取方

| 字段 | 权威来源 | 写入方 | 读取方 |
| --- | --- | --- | --- |
| `status`（实例态） | registry `instances.status`（观测回写） | `lifecycle.observe_status` → `registry.update_status`；`status.sync_status` | CLI `lwa status`、manager API、`status.py` 快照 |
| `desiredState` | manifest `desiredState`（用户意图） | 生命周期操作（start/stop/rebuild 成功路径）落盘 manifest + `upsert_from_manifest` | reconcile/daemon、CLI、管理页 |
| `lastOperation`（操作态） | registry `instances.last_operation_json`；镜像：manifest `lastOperation` | `build_queue._mark_queued/_mark_timeout/取消收尾`、`hosting._mark_failed`、host_container 成功路径、`update_last_operation` | `status.py` 快照 → CLI / manager API / 管理页 |
| `lastError` | registry `instances.last_error`（镜像 manifest `lastError`） | 各失败分支（排队超时、构建失败、验证失败） | CLI / 管理页 / 事件排查 |
| `containerId` / `imageId` | Docker 实际观测 | `host_container` 第 7 步观测后写 manifest + registry；停机/重建前由 S2-01 语义清空 | start/restart 轻量恢复路径、drift 检测 |
| `hostPort` | registry `ports` 表 + manifest `network.hostPort` | `PortAllocator`（分配/复用/释放）、`host_container` 成功路径 | 网关渲染、健康检查、CLI/API |
| 路径别名（`routeHost`/`routeUrl`） | manifest `network`（登记）+ Caddy 片段（生成物） | `path_alias` 登记/换别名/守卫回滚 | 网关渲染、活验证、管理页入口 |
| 配置指纹（`deploymentFingerprints`） | manifest `deploymentFingerprints` | `lifecycle._compute_deployment_fingerprints`（渲染生成物后计算） | start/restart/recover 指纹判定（S2-04 收敛） |

边界说明：`status` 唯一合法写入方是观测链（`observe_status`/`sync_status` 及其
stale 回收）与「真实改变服务存在性」的操作成功/失败收尾（如 stop 后回写
stopped）。排队（queued）、取消（cancelled）、构建失败不再写 `status`。

## 4. 代码改动清单

1. `models.py`：`InstanceManifest.lastOperation: dict | None`。
2. `registry/connection.py`：schema v6 `ALTER TABLE instances ADD COLUMN
   last_operation_json TEXT`；`CURRENT_SCHEMA_VERSION = 6`。
3. `registry/dao.py`：`upsert_from_manifest` 同步该列；新增
   `update_last_operation(instance_id, operation)`。
4. `build_queue.py`：`_mark_queued` / `_mark_timeout` 不再 `update_status`，
   改 `update_last_operation`（+ `last_error` 与事件保留）；取消路径
   （queued→cancelled、cancelling 中间态、cancel_failed、`_update_instance_cancelled`）
   同样只写操作态。
5. `hosting.py`：`_mark_failed` 增加操作态记录（保留 failed——停机后确实未在服务，
   与观测一致）；`host_container` 成功路径写 `lastOperation=succeeded`，
   停机中止分支（S2-01）补记 `lastOperation=failed`；`build_and_host_frontend`
   成功/失败/取消三处对齐。
6. `status.py`：`InstanceStatus.last_operation`，`to_dict()` 输出 `lastOperation`。
7. `cli/status.py`：实例行下输出「最近操作：…失败（时间）原因」。
8. `manager_static/helpers.js` + `app.js` + `style.css`：状态徽标旁叠加
   「最近一次{kind}失败」徽标；详情页基本信息区展示操作态一行。
9. 测试：`tests/scripts/test_bug750_759_operation_state.py`（翻转
   `repro.py::test_57_queue_status_only_updates_registry`、排队超时实例仍 running、
   序列化/快照/CLI 回归、`_mark_failed` 操作态）；更新
   `tests/scripts/test_build_queue.py` 两处旧断言。
10. 文档：`docs/manager-page.md`、`docs/agent-guide.md` 状态字段说明。

## 5. 风险与遗留

- `sync_status` 仍跳过 `QUEUED`/`PENDING` 实例；改后实例不再进入 queued，
  该跳过仅剩 pending，行为无害。
- 管理页 `isActionableStatus` 仍含 `failed`：排队超时后实例不再 failed，
  「待处理」筛选自然不再收纳这类实例（这正是 D4 语义）。
- daemon reconcile 对 `cancelled` 实例的处理依赖 `desiredState` 而非 status，
  取消路径改操作态不影响自愈。

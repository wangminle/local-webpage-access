# 锁心跳载荷一致性设计

## 问题

`_touch_lock_heartbeat` 使用 `seek -> truncate -> write` 原地刷新锁文件。并发读者可以在 `truncate` 与 `write` 之间看到空文件或不完整载荷，导致测试偶发 `IndexError`，锁状态诊断也可能短暂降级。核心互斥由同一 inode 上的文件锁保证，不受此问题影响。

## 方案

1. 心跳写入复用 `file_lock.write_lock_payload`：先写入完整新载荷，再按载荷长度截断，不再先清空文件。
2. 在 `lifecycle` 中统一解析 PID/时间戳载荷；读到空内容、单行或非法值时做有界重试。持续单行但 PID 合法时保留 PID 并返回零时间戳，供现有 mtime 逻辑兜底；完全无效时返回无载荷安全降级。
3. 保持锁文件 inode 不变，不使用 `replace` 或 `unlink`，继续满足 BUG-213 的跨进程互斥约束。

## 测试

- 在真实 `os.ftruncate` 边界观测文件内容，并强制要求观测点发生；旧实现因未经过写后截断路径而稳定失败。
- 验证修复后心跳刷新不会在截断前清空文件，且 PID/时间戳仍正确更新。
- 验证统一读取在首次遇到不完整载荷时能重试成功，在持续单行时保留 PID 供 mtime 兜底，持续无效时安全降级。
- 运行定向、全量、ruff、mypy 与台账校验。
